S0 · One more building block

Week 5's table of how P4 differs mentioned "a few explicit stateful objects (registers, counters, meters)". You haven't used them yet, and most of today's examples depend on them.

A register is an array in the switch's memory that the data planedata planeThe part of a network device that forwards packets, at full speed, using tables it has been given. can both read and write, packet by packet, at line rateline rateThe full speed of a link. Forwarding at line rate means keeping up with every packet the link can carry, even the smallest ones, back to back.. Tables are different: the data plane only reads them, and the control planecontrol planeThe part of a network that decides how traffic should be forwarded — routing protocols or an SDN controller — and fills in the data plane's tables. writes their entries. With registers, a switch can remember what it has seen — how many packets a flow has sent, which server a connection went to, a running total.

register<bit<32>>(1024) flow_count;      // 1024 counters, kept from packet to packet

action count_flow() {
    bit<32> i;
    bit<32> n;
    hash(i, HashAlgorithm.crc32, (bit<32>)0,
         { hdr.ipv4.srcAddr, hdr.ipv4.dstAddr }, (bit<32>)1024);
    flow_count.read(n, i);                // read this flow's counter...
    flow_count.write(i, n + 1);           // ...and write it back, one higher
}

Add custom headers and parser states, tables, hashes, multicast, and recirculation — sending a packet through the pipeline a second time — and you have the whole toolkit. Every system below is built from it, and every one is shaped by Week 5's limits: a fixed amount of memory in each stage, a fixed number of stages, no loops and no floating point.

S1 · Moving traffic

Load balancing and recovering from failures are the network's own jobs. These three do them better by keeping state in the switch:

P4 at work: Moving traffic

SilkRoad · a load balancer inside the switch

The problem
A service's virtual IP address is shared by many servers. Software load balancers — often hundreds of servers' worth — spread connections over them, and must keep every connection on the same server even while servers are added and removed.
What the switch does
The switch maps each virtual IP to a pool of servers and remembers every connection in a table, so a connection stays put when the pool changes. New connections are reported to the switch's own CPU, which adds their entries; a small filter in registers covers the moment before an entry exists.

What it uses from the pipeline

  • custom header + parser (not used)
  • tables (used)
  • registers (used)
  • hash (used)
  • multicast / mirror (not used)
  • recirculate (not used)
  • control plane (used)
  • tables: ConnTable, an exact match on a short hash of the five-tuple, plus tables for virtual IPs and server pools
  • registers: a Bloom filter remembering connections whose entries are still being installed
  • hash: a 16-bit digest of the five-tuple is the connection's key, to save table memory
  • control plane: the switch CPU writes each new connection's entry — much slower than the data plane, hence the filter

Reported result

One switch ASIC can replace up to hundreds of software load balancers, potentially cutting cost by over two orders of magnitude. About 400 lines of P4 balance ten million connections at line rate (on Tofino).

The catch: Hash digests and the Bloom filter can collide, so some new connections need the CPU to sort them out.

Where you've seen this: ECMP's hashing (Fundamentals F3) — but with memory, so a changing server pool doesn't move existing connections. And Week 5's run-time tables, filled here by the switch's own CPU.

Miao et al., "SilkRoad: Making Stateful Layer-4 Load Balancing Fast and Cheap Using Switching ASICs", ACM SIGCOMM 2017.

Quick check

SilkRoad keeps a table entry for every connection. Why not simply hash each packet's five-tuple onto the pool of servers, as ECMP does for paths?

S2 · Serving applications from the network

These two take on work that used to belong to servers. Both rely on Week 5's protocol independence: the switch parses a header that only their application uses.

P4 at work: Serving applications

NetCache · the switch answers the hottest reads

The problem
In a key-value store, a few keys get most of the requests. The servers holding them are overloaded while others sit idle — and which keys are hot keeps changing.
What the switch does
The top-of-rack switch in front of the storage servers keeps the hottest items. A read for a cached key is answered by the switch itself; a write invalidates the cached copy, so it never serves stale data. Hot keys that aren't cached yet are spotted in the switch and reported to its controller, which swaps them in.

What it uses from the pipeline

  • custom header + parser (used)
  • tables (used)
  • registers (used)
  • hash (used)
  • multicast / mirror (not used)
  • recirculate (not used)
  • control plane (used)
  • custom header + parser: a NetCache header — operation, sequence number, key, value — on a reserved port, with its own parser state
  • tables: an exact match on the key: is it cached, and where is its value?
  • registers: the values themselves, spread across register arrays in several stages, and a hit counter per key
  • hash: a count-min sketch and a Bloom filter spot hot keys that aren't cached yet
  • control plane: the controller inserts and evicts cached keys

Reported result

One switch serves over 2 billion queries a second for 64,000 items with 16-byte keys and 128-byte values. Throughput is 3–10× higher, and latency halves for up to 40% of queries (on Tofino).

The catch: One storage rack only; small keys and values only; and workloads that are both skewed and write-heavy gain little.

Where you've seen this: Week 5's protocol independence: the switch parses a key-value header that no standard has ever heard of. Its hot-key detector is the sketch in the simulator below.

Jin et al., "NetCache: Balancing Key-Value Stores with Fast In-Network Caching", ACM SOSP 2017.

Quick check

NetCache's switch holds only tens of thousands of items, for a store with millions of keys. Why does such a small cache help so much?

S3 · Computing for machine learning

Here the switch doesn't only forward or answer: it computes.

P4 at work: Computing for machine learning

SwitchML · the switch adds up the gradients

The problem
Training a model on many machines spends much of its time exchanging gradients: every worker needs the sum of all the workers' updates, after every step.
What the switch does
Workers stream their gradients in small chunks. The switch adds each chunk from every worker into a slot from a fixed pool, and when all the workers have contributed, multicasts the sum back to all of them at once — one exchange instead of many.

What it uses from the pipeline

  • custom header + parser (used)
  • tables (not used)
  • registers (used)
  • hash (not used)
  • multicast / mirror (used)
  • recirculate (used)
  • control plane (not used)
  • custom header + parser: a custom header carrying the slot index and the chunk's offset
  • registers: the slot pool of partial sums, counters, and a bitmap of which workers have contributed
  • multicast / mirror: multicast returns each finished sum to every worker
  • recirculate: packets recirculate through the pipelines to handle a whole chunk

Reported result

Training up to 5.5× faster on real-world benchmark models than PyTorch or TensorFlow with NCCL (on Tofino, with 8 workers).

The catch: P4 has no floating point, so workers scale their gradients to integers first. One switch aggregates one rack, and its few tens of megabytes of memory force the streaming slot design.

Where you've seen this: Week 5's comparison table: no floating point, and fixed memory. SwitchML is designed around both.

Sapio et al., "Scaling Distributed Machine Learning with In-Network Aggregation", USENIX NSDI 2021.

Quick check

Why do SwitchML's workers convert their gradients to integers before sending them?

S4 · Watching and defending

Measurement and security need the switch to notice patterns across many packets — which flows are big, which sources are attacking — with very little memory.

P4 at work: Watching and defending

Sonata · telemetry questions, answered partly in the switch

The problem
Operators want to ask questions of live traffic — is someone scanning our hosts? who is sending odd DNS? — but sending every packet to software can't keep up, and fixed telemetry can't answer new questions.
What the switch does
Operators write each question as dataflow steps: filter, map, reduce, distinct. A planner runs as many steps as fit in the switch and sends only the much smaller remainder to a stream processor (Spark), refining the question as it runs.

What it uses from the pipeline

  • custom header + parser (not used)
  • tables (used)
  • registers (used)
  • hash (used)
  • multicast / mirror (used)
  • recirculate (not used)
  • control plane (used)
  • tables: filter and map steps become match-action tables, updated every time window
  • registers: reduce and distinct keep per-key state in register arrays
  • hash: a hash picks each key's register cell, with collisions handled
  • multicast / mirror: matching packets are mirrored to a monitoring port and turned into records
  • control plane: the runtime rewrites the filter tables at the end of each window

Reported result

Supports a wide range of telemetry tasks while cutting the stream processor's workload by up to seven orders of magnitude (on Tofino and BMv2).

The catch: Each query is compiled to one switch, and some operations — such as dividing to get an average — can't run in the switch.

Where you've seen this: Week 5's In-band Network Telemetry wrote measurements into packets. Sonata goes a step further: it answers questions inside the switch, with the same registers and hashes.

Gupta et al., "Sonata: Query-Driven Streaming Network Telemetry", ACM SIGCOMM 2018.

S5 · What they have in common

  • Small state, where every packet already passes. None of these needs much memory. All of them gain from acting on every packet at line rate, without a trip to a server.
  • Shaped by the silicon. Values must be small (NetCache), sums must be integers (SwitchML), counts are approximate (the sketches), and state is lost if a switch fails (P4xos). Recirculation buys extra stages, at the cost of bandwidth.
  • The hardware moves on. Most of these ran on Intel's Tofino, which is no longer being developed (Week 5). The ideas carry over to SmartNICs and DPUs — Part 6 of today's lecture.

Discuss

1 · Topology without rewiring

Picture a data centre: thousands of servers in racks, running virtual machines and containers for hundreds of customers — tenants. Every tenant wants a network of its own:

  • its own addresses, even if they overlap with another tenant's 10.0.0.0/8;
  • its own layer-2 segments, isolated from everyone else's;
  • machines that can move to another server, in another rack, without changing their address.

The physical network can't be rewired every time a tenant changes its mind. Modern data-centre networks are routed IP fabrics, built once and kept simple. And the old tool for separating networks, the VLAN, runs out: its ID has only 12 bits.

The answer is to stop tying the logical topology to the wiring. An overlay is a virtual network built by tunnelling across an underlay, the real IP network:

In this week's labMininet's switch and 10.NN.0.0/24The tunnel between h1 and h2, 10.NN.100.0/24

It's a familiar move: separate two concerns so each can change without the other — like the data and control planes in Week 4. And you've already seen it start. In Week 5 Step 5, your switches delivered a packet addressed to h3 to h2, because they forwarded on the tunnel header and ignored the IP address inside. An overlay does the same, at the scale of a data centre.

2 · VXLAN, header by header

VXLAN (standardised in 2014) is the most widely used overlay in data centres. It carries whole Ethernet frames inside UDP packets. Two terms do most of the work:

  • a VTEP (VXLAN tunnel endpoint) wraps frames on the way into the tunnel and unwraps them on the way out. It can be a hypervisor's virtual switch, a top-of-rack switch — or, in your lab, a Linux host;
  • the VNIVNIVXLAN Network Identifier: a 24-bit number in the VXLAN header that says which virtual network a frame belongs to. (VXLAN network identifier) says which overlay network a frame belongs to. It has 24 bits: about 16 million networks, against the VLAN's 4,094.

Two details worth knowing. VXLAN's official UDP port is 4789, but Linux's default is 8472, chosen before the standard existed. 3 · A VTEP as a P4 program

Week 5 ended with a question: which parts of a P4 program would you add or change to put a packet into a VXLAN tunnel, and take it out again? Here's the answer, as a program. It's a working VTEP, tested on BMv2BMv2The P4 reference software switch (behavioral model version 2), for running P4 programs without hardware. against a Linux VXLAN tunnel like the one in the lab, with pings crossing in both directions. The full program is vtep.p4; these are the parts that matter.

Headers and the parser

Headers. Two new ones, UDP and VXLAN — and two of everything else: the outer headers, and the tenant's frame inside.

header udp_t   { bit<16> srcPort; bit<16> dstPort; bit<16> length; bit<16> checksum; }
header vxlan_t { bit<8> flags; bit<24> reserved; bit<24> vni; bit<8> reserved2; }

struct headers {
    ethernet_t ethernet;          // outer, once the packet is in the tunnel
    ipv4_t     ipv4;
    udp_t      udp;
    vxlan_t    vxlan;
    ethernet_t inner_ethernet;    // the tenant's frame
    ipv4_t     inner_ipv4;
}

The parser. New states continue the chain of headers (Fundamentals F1): IPv4's protocol 17 leads to UDP, port 4789 leads to VXLAN, and after VXLAN comes the tenant's frame.

state parse_ipv4 {
    packet.extract(hdr.ipv4);
    transition select(hdr.ipv4.protocol) { 17: parse_udp; default: accept; }
}
state parse_udp {
    packet.extract(hdr.udp);
    transition select(hdr.udp.dstPort) { 4789: parse_vxlan; default: accept; }
}
state parse_vxlan {
    packet.extract(hdr.vxlan);
    transition parse_inner_ethernet;    // then the inner Ethernet and IPv4 headers
}

Into the tunnel, and out

Into the tunnel. A table keyed on where the frame came from and which MAC addressMAC addressThe hardware address of a network interface, such as 00:00:00:00:00:01. Ethernet switches forward frames by MAC address. it's for. Its action pushes the headers: in P4, pushing a header means setValid() and filling in its fields.

table vtep_encap {
    key = { standard_metadata.ingress_port: exact; hdr.ethernet.dstAddr: exact; }
    actions = { encap; drop; }
    default_action = drop();
}

action encap(bit<24> vni, ..., ip4Addr_t my_vtep, ip4Addr_t remote_vtep, ...) {
    hdr.inner_ethernet = hdr.ethernet;      // the tenant's frame moves inside
    hdr.inner_ipv4 = hdr.ipv4;
    hdr.vxlan.setValid();                   // push VXLAN...
    hdr.vxlan.vni = vni;
    hdr.udp.setValid();                     // ...and UDP
    hdr.udp.dstPort = 4789;
    hash(hdr.udp.srcPort, ...,              // a hash of the inner flow
         { hdr.inner_ipv4.srcAddr, hdr.inner_ipv4.dstAddr, hdr.inner_ipv4.protocol }, ...);
    hdr.ipv4.srcAddr = my_vtep;             // the old IPv4 header becomes the outer one
    hdr.ipv4.dstAddr = remote_vtep;
    hdr.ipv4.protocol = 17;
    hdr.ipv4.ttl = 64;                      // a fresh TTL for the trip across the underlay
    // ...plus lengths, outer MAC addresses and the output port: see vtep.p4
}

Out of the tunnel. A second table, vtep_decap, is keyed on the VNI and the inner destination MAC. Its action does the reverse: it copies the inner headers back to the outside and calls setInvalid() on the rest — popping them.

The deparser

The emit order is the encapsulation. A header that isn't valid isn't written, so the same six lines send out a plain frame or a tunnelled one:

packet.emit(hdr.ethernet);
packet.emit(hdr.ipv4);
packet.emit(hdr.udp);
packet.emit(hdr.vxlan);
packet.emit(hdr.inner_ethernet);
packet.emit(hdr.inner_ipv4);

Everything from Week 5 is here: parser states that must agree with the deparser — Step 6's lesson — tables the program only declares, and actions that rewrite headers. Notice what's not in the program: which tenant MAC sits behind which VTEP.

4 · Finding the other end

When a frame for host B arrives at a VTEP, the VTEP has to know which remote VTEP B is behind: in the P4 program, that's the entries in vtep_encap. In the lab you'll tell Linux by hand: one tunnel, one remote address. With thousands of hosts that come and go, there are two real ways to fill that table:

  • Flood-and-learn — the original VXLAN approach. BUM trafficBUM trafficBroadcast, unknown-unicast and multicast traffic: frames a switch or VTEP has to send to every possible destination, because it can't pick just one. (broadcasts, unknown unicasts and multicasts) is sent to every VTEP in the VNI, and each VTEP learns MAC address → VTEP from the packets it receives. It's Week 1's learning bridge, stretched across the underlay: the table is filled from the traffic itself, in the data plane.
  • EVPN — VTEPs advertise the MAC and IP addresses of their own hosts in BGP, so every VTEP knows where everything is before any traffic flows. A VTEP can even answer ARPARPAddress Resolution Protocol: how a host finds the MAC address for an IP address on its local network — it broadcasts a request, and caches the reply. requests itself. The table is filled by the control plane.

EVPN is the same shift you saw with SDNSDNSoftware-Defined Networking: taking the control plane out of individual switches and running it as software, often on a logically centralised controller. in Week 4 — learning moves out of the data plane and into a control plane — but done with a distributed protocol, BGP, rather than a central controller. Many data-centre fabrics today run VXLAN with EVPN; others use an SDN controller to program the VTEPs directly.

On a P4 switch, even flood-and-learn needs help from the control plane. In v1model, the Week 5 lab's architecture, the data plane can read its tables but can't add entries to them. A P4 VTEP that learns sends a digest — a short message with the new MAC address and where it came from — up to its controller, which writes the entry back down at run time. Week 5's split between compile time and run time decides how learning has to work.

5 · What tunnelling costs

Tunnels aren't free: VXLAN costs 50 bytes a packet (Fundamentals F1 compares it with other tunnels). In practice the costs come in three kinds.

Smaller packets

Inside a VXLAN tunnel, each packet also carries the inner Ethernet header (14 bytes), VXLAN (8), UDP (8) and the outer IP header (20). So on a 1500-byte underlay, the overlay gets 1450. (The diagram in Part 2 counts the outer Ethernet header instead, because it shows the frame on the wire; the MTU counts IP packets, so the inner Ethernet header is what matters. It's 50 bytes either way.) Data centres often avoid the squeeze by giving the underlay jumbo frames of 9000 bytes.

The real danger is a mismatch. Path MTU discoverypath MTU discoveryHow a sender finds the largest packet that fits the whole path: routers that can't forward a too-big packet send back an ICMP error saying what fits. It fails when nothing is sent back. (Fundamentals F2) depends on an error coming back from a router. But if the too-small link is just a link — no router — the frame is simply dropped as it arrives, and nothing comes back. Small packets get through; big ones vanish. That's a black hole, and you'll create one in the lab. (A P4 switch that pushes a header without planning for it makes the same kind: see why a P4 switch can only drop it.) Try it here first:

Quick check

In the lab's MTU mismatch, small pings across the overlay still work, but a TCP transfer almost stops. Why?

Hidden flows

Underlay routers spread traffic over equal-cost paths by hashing each packet's five-tuple: ECMP (Fundamentals F3). But every packet between two VTEPs has the same outer addresses. If the outer headers were all identical, thousands of tenant flows would hash onto a single path. VXLAN's answer is the UDP source port: the VTEP sets it from a hash of the inner headers — the hash() call in Part 3's encap action — so each inner flow looks different on the outside.

The same blindness applies to anything else in the underlay that inspects packets: firewalls, quality-of-service rules and monitoring all see only the outer headers. It's Week 5's parser lesson again: a device that doesn't know a header can't see past it. A programmable underlay switch could fix that itself — add parser states for port 4789, VXLAN and the inner headers, and it can hash, filter or count on the tenants' own flows. A fixed-function chip can only do that if it was built knowing VXLAN.

Quick check

The underlay spreads traffic over several equal paths (ECMP) by hashing packet headers. Two VTEPs exchange thousands of different overlay flows. What lets those flows use different paths?

Harder troubleshooting

Every problem now has two layers of addresses and two places to be. Is the fault in the overlay, the underlay, or the mapping between them? A traceroute inside the overlay shows the whole underlay as a single hop: the underlay's routers decrement the outer TTL, never the inner one. A capture on the underlay shows UDP to port 4789: tcpdump decodes it as VXLAN only because the port is the standard one. Good overlay troubleshooting means checking both layers, deliberately. In-band Network TelemetryIn-band Network TelemetrySwitches write measurements — such as queue depth and time spent — into the packets they forward, so each packet carries a record of its own journey., from Week 5, is one way to look inside: underlay switches write their own measurements into the packets as they pass, so the endpoints see what happened along the way.

6 · Network functions in software

Firewalls, load balancers, NAT gateways and VPN concentrators used to be dedicated boxes, each racked and cabled by hand. NFVNFVNetwork Functions Virtualisation: running network functions such as firewalls and load balancers as software instead of dedicated appliances. (network functions virtualisation) runs the same functions as software on ordinary servers, in virtual machines or containers.

The gains are the ones every software system has: deploy in minutes, scale out by adding instances, give each tenant its own chain of functions, and upgrade without a site visit. The loss is speed. Week 3's time budget hasn't gone away: a 10 Gb/s link full of minimum-size packets delivers about 15 million packets a second — 67 nanoseconds each. The normal Linux network stack pays for every packet with an interrupt, memory copies and crossings between kernel and application. In practice it handles on the order of a million packets a second per core, not fifteen.

Wrap-up

Key takeaways

  • Programmable switches already do far more than forward: load balancing, caching, consensus, ML aggregation, telemetry and DDoS defence. Each keeps a little state in registers, and each is shaped by the pipeline's limits.
  • Every header names the next. A tunnel pushes headers at its entrance and pops them at its exit, and every byte it adds comes out of the MTU.
  • Overlays separate the topology tenants see from the physical wiring. The underlay only has to route IP between tunnel endpoints.
  • VXLAN wraps a whole Ethernet frame in UDP, port 4789, adding 50 bytes. The 24-bit VNI allows about 16 million overlay networks.
  • Week 5's tunnel needed every switch to understand it, and had no loop protection. VXLAN puts an ordinary IP header outside, so only the endpoints parse it — and the outer TTL stops loops.
  • A VTEP is a P4 program like any other: parser states for UDP and VXLAN, a table whose action pushes headers, and a deparser whose order is the encapsulation. Which host sits behind which VTEP is run-time state.
  • Flood-and-learn fills that state from traffic; EVPN advertises it in BGP before traffic flows: data-plane learning versus control-plane learning.
  • Tunnels cost MTU, hide flows from the underlay — which the UDP source-port hash works around — and add a layer to every problem. An MTU mismatch with no error coming back is a black hole for big packets, and a P4 switch can't fragment its way out.
  • NFV trades throughput for flexibility. Kernel bypass — DPDK, XDP, SR-IOV — and programmable NICs win back speed, at the cost of dedicated cores, hardware and tooling.
  • Network namespaces, veth pairs and bridges are the building blocks of Mininet and of containers alike.

F2 · Too big for the link

A link's MTU (maximum transmission unit) is the largest IP packet it carries: 1500 bytes on standard Ethernet. It counts from the IP header onwards. The link's own Ethernet header comes on top, so a full-size frame is 1514 bytes.

You'll measure MTUs with ping. Its -s option sets only the ICMP data; the ICMP header (8 bytes) and the IPv4 header (20) come on top. So ping -s 1472 sends exactly a 1500-byte packet.

When a packet doesn't fit

What does a router do with a packet that's too big for the next link?

The packetWhat the router does
IPv4, don't-fragment bit offSplits it into fragments, which the destination puts back together
IPv4, don't-fragment bit onDrops it, and sends back an ICMP fragmentation needed error giving the MTU that fits
IPv6Drops it, and sends back ICMPv6 packet too big: in IPv6, only the sender may fragment

Most TCP traffic sets don't-fragment, and uses those errors to learn the largest size the whole path can carry: path MTU discovery. It works as long as the error comes back. The lecture shows what happens when it doesn't. (ping -M do sets don't-fragment. If your own interface is too small, your host doesn't even send the packet: ping says message too long, mtu=….)

Why a P4 switch can only drop it

A P4 switch can't fragment. Splitting a packet means walking through its payload and turning one packet into several — and a pipeline with a fixed number of stages and no loops, which never even parses the payload, has no way to do that. So if a switch pushes Week 5's 4-byte header onto a full 1500-byte packet, the 1504-byte result doesn't fit the next link, and it's lost. Unless the program sends an error itself, nothing tells the sender. A tunnel has to plan for its overhead in advance; a P4 switch can't repair it afterwards.

Quick check

On a 1500-byte link with no tunnel, you run ping -M do -s 1473 to a neighbour. What happens?

F3 · Hashing and equal-cost paths

In Week 3's lab, r1 had two paths towards h2's network, and your static routes used only one. Real networks use both. When a router has several equal-cost paths to a destination, ECMP (equal-cost multi-path) spreads the traffic across them.

It doesn't alternate packet by packet. It hashes fields that stay the same for a whole flow — usually the five-tuple: source and destination address, protocol, source and destination port — and the hash picks the path. Every packet of one TCP connection gives the same hash, so it takes the same path and arrives in order; different connections land on different paths.

In P4, that's a hash() over the header fields, choosing from a table of next hops that the control plane fills at run time — Week 5's split between compile time and run time again. Keep the five-tuple in mind: in the lecture, a tunnel hides it.

Quick check

A router has two equal-cost paths to a destination. Why does ECMP hash each packet's addresses and ports to choose one, instead of simply alternating packets between them?

Part 4 — Measure the cost of tunnelling

MTUMTUMaximum Transmission Unit: the largest packet an interface can send in one piece — 1500 bytes on standard Ethernet.. Compare h1 ip link show h1-eth0 (1500) with h1 ip link show vxlan100 (1450): the kernel took 50 bytes off for the VXLAN headers. Confirm the limit with "don't fragment" pings:

h1 ping -M do -c 1 -s 1422 10.NN.100.2
h1 ping -M do -c 1 -s 1423 10.NN.100.2

The first works (1422 + 28 bytes of headers = 1450); the second reports message too long, mtu=1450.

Throughput. Start an iperf3 server on h2, then compare the underlay with the overlay:

h2 iperf3 -s -D
h1 iperf3 -c 10.NN.0.2 -t 5
h1 iperf3 -c 10.NN.100.2 -t 5

Record both receiver rates. The overlay is noticeably slower: every packet is encapsulated and decapsulated, and each carries 50 fewer bytes of payload. Both numbers are far higher than a real link because nothing leaves your laptop — the ratio is what matters.

Part 6 — Break it with an MTU mismatch

Simulate someone reducing the underlay MTU on h2's side:

h2 ip link set h2-eth0 mtu 1400

Now test from h1: small pings (h1 ping -c 2 10.NN.100.2), large pings (h1 ping -c 2 -s 1400 10.NN.100.2) and a TCP transfer (h1 iperf3 -c 10.NN.100.2 -t 5). Small pings still work, but large pings fail completely and the transfer collapses to almost nothing — a black hole that only swallows big packets. Diagnose it as if you didn't know the cause:

  • Find the size limit. Repeat h1 ping -M do -c 1 -s <size> 10.NN.100.2, narrowing in on the largest size that works. Add 28 bytes (inner IP and ICMP headers) and 50 bytes (VXLAN overhead) and compare with the underlay MTUs. You'll land 4 bytes above h2's 1400 — 1326 is the largest size that works, not 1322. That's not your mistake: a receiving Linux interface accepts frames up to 4 bytes over its MTU, leaving room for a VLAN tag. The packets that die are the ones beyond that allowance.
  • Find where packets die. Check sh cat /sys/class/net/s1-eth2/statistics/tx_dropped and h2 cat /sys/class/net/h2-eth0/statistics/rx_dropped before and after a few large pings. Both count up together: the switch sends the frames towards h2, and they're discarded as they arrive.
  • Fix it: h2 ip link set h2-eth0 mtu 1500, then rerun the large ping and iperf3.

Linux protects the tunnel MTU

You can't produce this failure the other way round: h1 ip link set vxlan100 mtu 1500 is refused with Invalid argument, because Linux won't let the tunnel MTU exceed what its underlay interface can carry. A device elsewhere on the path has no such protection.

Type exit, then exit again to leave the container.

Part 7 — Containers: namespaces plus a filesystem

From now on, the course runs real network software in Docker containers. Here's what a container is, in the same terms. On your laptop (not inside the lab container):

docker run -d --name c1 alpine:3.20 sleep 600
docker exec c1 ip addr show eth0
docker exec c1 cat /etc/os-release
docker exec c1 ps
docker rm -f c1
  • ip addr shows eth0@if…: a veth pair, with the other end plugged into Docker's bridge — exactly what you built in Part 2.
  • /etc/os-release says Alpine Linux, not your laptop's OS: the container has its own filesystem.
  • ps lists only the container's own processes: it has its own process namespace too.

A container is a set of namespaces plus a filesystem image. That's why a router's software can be packaged as a container, and why the labs from Week 7 on use them.

  3. Why did small pings keep working during the MTU mismatch while TCP almost stopped?

D5 — Evidence from the running overlay

Collect it in this order, starting each network fresh. The commands use the starting design's names: a tenant that spans three hypervisors (red), a VM on one of them (red1 on hv1) and its tenant-mate on a second (red2, 10.NN.50.11, on hv2). Use your own names and addresses where yours differ.

Flood and learn — on a fresh python3 build_overlay.py overlay.yaml, before you send anything else:

sh echo "== hv1: vxlan100 before any traffic" > evidence6/flood.txt
hv1 bridge fdb show dev vxlan100 >> evidence6/flood.txt

red1 ping -c 2 10.NN.50.11 >> evidence6/flood.txt
sh sleep 8; echo "== captured on hv3's underlay" >> evidence6/flood.txt; cat /tmp/hv3.txt >> evidence6/flood.txt
sh echo "== hv1: vxlan100 after" >> evidence6/flood.txt
hv1 bridge fdb show dev vxlan100 >> evidence6/flood.txt
sh echo "== hv3: vxlan100 after" >> evidence6/flood.txt
hv3 bridge fdb show dev vxlan100 >> evidence6/flood.txt

Before the ping, the VTEP table holds only 00:00:00:00:00:00 entries: the flood list your code created. Look at what hv3 captured — although the ping was between hv1 and hv2 — and at what each table has learned afterwards.

Isolation — in the same network, ping an address that both tenants use, while capturing on the other tenant's VM with that address (blue2, also 10.NN.50.11):

blue2 timeout 8 tcpdump -ni blue2-eth0 > /tmp/blue2.txt 2>&1 &
red1 ping -c 3 10.NN.50.11 > evidence6/isolation.txt
red1 ip neigh show 10.NN.50.11 >> evidence6/isolation.txt
sh sleep 8; echo "== captured on blue2 meanwhile" >> evidence6/isolation.txt; cat /tmp/blue2.txt >> evidence6/isolation.txt
blue1 ping -c 2 10.NN.50.11 >> evidence6/isolation.txt
blue1 ip neigh show 10.NN.50.11 >> evidence6/isolation.txt

The MAC addresses tell you which VM answered: each has its tenant's VNI in the middle. Type exit.

The black hole — build your copy anyway: python3 build_overlay.py blackhole.yaml --force. Then:

red1 ping -c 2 10.NN.50.11 > evidence6/blackhole.txt
red1 ping -c 2 -W 1 -s 1472 10.NN.50.11 >> evidence6/blackhole.txt
red2 iperf3 -s -D
red1 timeout 20 iperf3 -c 10.NN.50.11 -t 5 >> evidence6/blackhole.txt 2>&1

Then find the limit: repeat red1 ping -M do -c 1 -W 1 -s <size> 10.NN.50.11 >> evidence6/blackhole.txt, narrowing in on the largest size that works, and save the largest that works and the smallest that doesn't. Type exit.

Two fixes — build mtu_a.yaml, and save the same measurements, labelled:

red1 iperf3 -c 10.NN.50.11 -t 5 >> evidence6/fixes.txt

Type exit, build mtu_b.yaml, and do the same under == fix B: underlay MTU 9000, with sizes 1472 and 1473.

Troubleshooting

  • Mininet complains that an interface already exists (after a crash): run mn -c, then build again.
  • build_overlay.py says tenant_commands() returned no commands: it hasn't been written yet — look for TODO.
  • A ping between two VMs of the same tenant fails: look at what your code printed for both hypervisors. Is the VM's port in the right bridge? Does each hypervisor's flood list name the other hypervisors?
  • The captures are empty: start tcpdump with & before the ping, and wait for its timeout before reading the file.
