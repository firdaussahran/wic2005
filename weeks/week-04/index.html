1 · Taking the control plane out of the box

Last week ended inside the forwarding hardware: a FIBFIBForwarding Information Base: the table the data plane actually uses to forward packets — the chosen best routes, arranged for fast lookup. that the data planedata planeThe part of a network device that forwards packets, at full speed, using tables it has been given. uses for every packet, filled in by a control plane running on the same box. Every router in a traditional network has its own control plane. OSPF is a distributed algorithm: each router swaps information with its neighbours and computes its own routes.

That design is robust, and it runs most of the Internet. But it has costs:

  • Behaviour emerges from many independent decisions. Predicting exactly what the whole network will do is hard.
  • Changing behaviour means changing configuration on every box — Week 1's problem.
  • New behaviour needs a new protocol, standardised and then implemented by every vendor. Week 3 showed the multi-year silicon gap; this is the same gap, in software.

The idea behind SDNSDNSoftware-Defined Networking: taking the control plane out of individual switches and running it as software, often on a logically centralised controller.: keep the data plane in the switches, but move the control logic out into ordinary software that programs every switch's tables through an open interface. The switches become simple and fast; the intelligence becomes a program you can change.

Logical vs physical centralisation

"Centralised" is ambiguous, and the difference matters:

  • Logically centralised — applications see one controller with one network-wide view, and program the network through it.
  • Physically centralised — the controller is one machine. One crash, and the network has no control plane.

Real controllers are logically centralised but physically distributed: a cluster of replicas sharing one view. That gives a simple programming model on top of a system that survives failures — at the price of keeping the replicas in agreement (Part 5).

Quick check

A controller runs as three replicas in three different data centres, sharing one view of the network. Is the control plane centralised?

2 · The controller as a platform

A computer's operating system hides the hardware behind abstractions — files, processes — and gives programs an APIAPIApplication Programming Interface: a defined way for programs to talk to a system — for example, a controller's REST API.. A controller does the same for a network, which is why it's often called a network operating system. It hides individual switches behind a network view: the topology, the hosts, the flows.

  • The southbound interfacesouthbound interfaceThe interface between a controller and the devices it controls, such as OpenFlow, P4Runtime, NETCONF or gNMI. connects the controller to the switches. This week it's OpenFlow. Later in the course you'll meet others that play the same role: P4RuntimeP4RuntimeAn API, carried over gRPC, that lets a controller load a compiled P4 program into a switch and write entries into its tables at run time., NETCONFNETCONFA network management protocol, usually over SSH, that exchanges YANG-modelled data as XML and supports transactions: candidate datastore, commit and locking. and gNMIgNMIgRPC Network Management Interface: gets, sets and streams YANG-modelled data over gRPC, using protobuf encoding..
  • The northbound APInorthbound APIThe interface between a controller and the applications that use it — usually a REST API. connects applications to the controller — routing, firewalling, load balancing — usually as a RESTRESTA style of web API: resources identified by URLs, manipulated with standard HTTP methods, with no session state kept on the server. API (Week 7).

The applications never talk to a switch directly. A firewall application says "block h1 from reaching h3", and the controller turns that into rules on whichever switches need them. Well-known controllers include NOX (the first, in 2008), Ryu, ONOS and OpenDaylight.

3 · OpenFlow: match–action

OpenFlow is the canonical southbound interface: a protocol that lets a controller read and write a switch's flow table directly. Each entry in the table, a flow, has:

PartWhat it isExample
Match fieldsHeader fields and their values; any field left out is a wildcardicmp,nw_src=10.0.0.1,nw_dst=10.0.0.3
PriorityWhich entry wins when several match: the highestpriority=40000
ActionsWhat to do with a matching packetoutput:2, FLOOD, drop, CONTROLLER, rewrite a field
CountersPackets and bytes that matchedn_packets=3
TimeoutsRemove the entry after it's idle, or after a fixed timeidle_timeout=60

Every packet is compared with the table, and the highest-priority matching entry decides what happens. A priority-0 entry with no match fields matches everything, so it catches whatever nothing else does: the table-miss entry. With no table-miss entry, unmatched packets are dropped.

That should look familiar: it's Week 3's TCAMTCAMTernary Content-Addressable Memory: hardware that compares a lookup key against every table entry at once, with "don't care" bits. Very fast, but expensive and power-hungry, so tables are small.. Wildcards are the * bits, and priority is row order. Since OpenFlow 1.1 a switch can also chain several tables into a pipeline, with each table able to pass the packet on to the next — and use groups: shared sets of actions. One kind, the fast-failover group, holds a backup port and switches to it by itself, the moment the main link goes down.

One abstraction, many devices

The power of match–action is that very different devices are the same table with different match fields:

Ethernet switchDestination MACOutput to one port

Two lessons from that table. First, two matching rules with the same priority are a bug: OpenFlow doesn't say which one wins. Second, a rule matches headers, not intentions. "h1 replies to h3's ping" has exactly the same addresses as "h1 pings h3", so the firewall rule blocks both.

5 · The hard problems

Moving control into software doesn't make the problems of distributed systems disappear. It moves them into the controller. These are the ones every SDN design has to answer.

Controller failure and the control channel

A switch keeps in touch with its controller over a TCP connection (port 6653), sending echo messages to check it's still there. When the replies stop, the switch must decide what to do, set by its fail-mode:

  • secure — keep the existing rules and never make up its own forwarding. New traffic that needs the controller fails.
  • standalone — fall back to being an ordinary learning switch, ignoring the controller's policy.

You'll see both in lab Steps 5 and 6.

Quick check

A switch enforces your firewall rules, and its controller becomes unreachable. Which fail-mode keeps the network safe, and what does it cost?

Keeping replicas consistent

A physically distributed controller has several copies of the network view. If the network between the replicas splits, they face the tension known from distributed systems as CAP. Either some replicas stop making changes until they can agree again (consistent, less available), or both sides carry on with different views (available, possibly installing conflicting rules). Production controllers use consensus protocols such as Raft to keep their core state in agreement, and accept the cost.

Updating without breaking

Even with one controller, changing a path means updating several switches — and the updates can't all land at the same instant. In between, packets meet a mix of old and new rules. Move this flow from A → B → D to A → C → D, and try each order:

Try it: change a path without losing packets

  1. 0 · Before: traffic goes A → B → D
  2. 1 · A: send the flow to C instead of B
  3. 2 · C: add a rule forwarding the flow to D
  4. 3 · B: remove the old rule

Packets flow: A → B → D.

The safe rule of thumb: update downstream switches first, so that no switch sends traffic to one that isn't ready. For harder cases, controllers use two-phase updates: install the new rules alongside the old, then switch all packets over at once by tagging them with a version.

Discussion: when a link fails

In the Week 3 assignment you took a link down and watched your static routes fail to recover, even though another path existed. Now picture that same link failing in three networks:

Static routesOSPFSDN controller

Fill in the table — on paper, or in your head — then compare answers.

Show discussion points

Static routes. Nobody notices — or rather, only the people whose traffic stops. Nothing changes until someone edits the routes by hand.

OSPF. The routers at each end of the link notice: at once if the interface goes down, or else when hello messages stop arriving — after the dead interval, 40 seconds by default on broadcast links, cut to well under a second when BFD is used. They flood the news, and every router recomputes its own routes. Because routers finish at slightly different times, short-lived micro-loops are possible while they converge.

SDN controller. The switch reports the dead port to the controller (a port-status message). The controller recomputes once, with a view of the whole network, and installs new rules on the switches that need them. Recovery time is detection, plus a round trip to the controller, plus the rule updates — and the update order above decides whether there's a brief blackhole on the way. If the control channel is lost at the same time, nothing changes at all: the switch's fail-mode decides what happens.

Best of both. With a fast-failover group, the controller pre-installs a backup path; the switch moves traffic to it by itself the instant the link dies, and the controller re-plans calmly afterwards. Local reaction for speed, central computation for a good path — and real networks mix the two in just this way.

Running out of table

Week 3 again: flow tables live in scarce TCAM. Reactive, per-flow rules can fill a table, and an attacker who sends many short new flows can fill it on purpose — while also flooding the controller with packet-inspacket-inAn OpenFlow message from a switch to its controller carrying a packet the switch doesn't know how to handle..

Scenarios for consideration

Four situations a real SDN deployment has to plan for. For each one, predict what happens — using the ideas listed under Use — before you open the discussion points.

Scenario A — a crash in the middle of an update

The controller is moving a flow from A → B → D to A → C → D, as in the update-order example. It has updated A, but crashes before updating C. The switches are in fail-mode secure, and their rules were installed proactively.

Use: update order, fail-mode, table-miss.

Show discussion points

A now sends the flow to C, but C has no rule for it. C's table-miss entry sends the packets to the controller — which is down — so the flow is blackholed until the controller comes back. Every other flow keeps working: secure keeps the existing rules. Updating C first would have left the old path working throughout; two-phase updates, with a version tag, avoid the problem entirely.

Scenario B — the controller cluster splits

The controller runs as three replicas that keep their state in agreement with a consensus protocol (Raft). A network fault splits them into a group of two and a group of one.

Use: logical vs physical centralisation, consistency.

Show discussion points

The side with two replicas still has a majority, so it carries on making changes. The single replica can't reach a majority, so it stops making changes rather than risk a conflicting view: consistency is chosen over availability. Switches connected only to that replica keep forwarding with the rules they have, but get no updates until the split heals — when the single replica catches up with the others.

Scenario C — a flood of new flows

An attacker sends 50,000 new, short flows a second into a network where the controller installs rules reactively.

Use: reactive vs proactive, table space, the controller as a target.

Show discussion points

The first packet of every new flow becomes a packet-in to the controller, so the controller's CPU is swamped — and every reactive rule takes space in the switch's flow table, which fills up. Legitimate new flows are delayed or dropped; existing flows keep working until their rules time out. Defences: proactive, wildcarded rules that need no packet-in, rate-limiting packet-ins at the switch (meters), eviction of idle entries, and detecting the attack.

Scenario D — one switch loses the controller

One switch loses its control channel; its data links are all fine. What happens to its traffic in fail-mode secure, and in standalone?

Use: fail-mode, security policy.

Show discussion points

In secure the switch keeps the rules it has, so existing traffic flows — but anything that needs the controller, such as a new flow in a reactive design, fails. In standalone it falls back to being an ordinary learning switch: everything keeps flowing, but the controller's policy is gone — a firewall rule that existed only in the controller no longer applies. It's a choice between availability and enforcing policy, and you see both behaviours in Steps 5 and 6 of this week's lab.

Centralisation concentrates risk

A controller that can program every switch is the most valuable target in the network. Whoever controls it controls all the traffic. Securing the control channel and the northbound API is part of the design, not an afterthought (Week 12).

6 · OpenFlow today

An honest framing

OpenFlow is taught here as an idea with lasting importance and very clear teaching value, not as what you'll find in most networks today. Learn the abstraction; don't expect to deploy OpenFlow as it was first designed.

OpenFlow mattered enormously. It gave SDN its name and showed that logically centralised control works at scale — Google's B4 network between its data centres is the best-known example. Open vSwitchOpen vSwitchA widely used software switch that supports OpenFlow. It's the switch in the Week 4 lab., driven by OpenFlow, still forwards traffic for virtual machines in many cloud platforms.

But most enterprise and campus networks never ran it. Vendor support was often partial, and the fixed list of match fields kept growing: about a dozen fields in OpenFlow 1.0, around forty in 1.3. Any new header still needed a new version of the standard and new switch support. That's Week 3's silicon problem, one level up. The answer was to make the parser and pipeline themselves programmable: P4P4A language for describing how a programmable switch parses and processes packets., next week.

The lasting ideas — separation of planes, a logically centralised view, match–action and an API to program it — are everywhere: in SD-WAN, data-centre fabric controllers, cloud networking, and P4Runtime.

Wrap-up

Key takeaways

  • SDN keeps the data plane in the switches and moves the control logic into software that programs them through an open interface.
  • Logically centralised (one view, one API) is not the same as physically centralised (one machine). Real controllers are the first, without being the second.
  • A controller is a network operating system: southbound to the switches, northbound to applications.
  • OpenFlow is match–action: the highest-priority matching entry wins, wildcards match anything, and a table-miss entry catches the rest. Equal-priority overlaps are undefined.
  • Reactive installation adapts but costs first-packet latency and controller load; proactive is fast and survives controller loss, but must be planned.
  • Centralising control moves the hard problems — failure, consistency, update order, table space and security — into the controller, but doesn't remove them.

Step 0 — An empty switch forwards nothing

Step 1 — A hub

sh ovs-ofctl add-flow s1 actions=flood
pingall

One rule with no match fields matches every packet and floods it out of every other port. Everything works again. Run sh ovs-ofctl dump-flows s1 and watch n_packets count up.

To see the cost of a hub, listen on h3 while h1 talks to h2:

h3 timeout 4 tcpdump -ni h3-eth0 icmp > /tmp/h3.txt 2>&1 &
h1 ping -c 3 h2
sh sleep 4; cat /tmp/h3.txt

h3 overheard the conversation between h1 and h2, even though none of it was addressed to h3.

Step 2 — A learning switch, written by hand

sh ovs-ofctl del-flows s1
sh ovs-ofctl add-flow s1 arp,actions=flood
sh ovs-ofctl add-flow s1 dl_dst=00:00:00:00:00:01,actions=output:1

sh ovs-ofctl add-flow s1 dl_dst=00:00:00:00:00:03,actions=output:3
pingall

Repeat the three tcpdump lines from Step 1: this time h3 captures nothing. This is the same table the Week 1 bridge built for itself — here you wrote it, and in Step 4 a controller will.

Step 3 — A firewall, and why priority matters

Block ICMP from h1 to h3:

sh ovs-ofctl add-flow s1 icmp,nw_src=10.NN.0.1,nw_dst=10.NN.0.3,actions=drop
h1 ping -c 3 h3

It still works. Run sh ovs-ofctl dump-flows s1: the drop rule shows n_packets=0. Both it and the dl_dst=…:03 forwarding rule have the default priority (32768), and both match the packet — and OpenFlow doesn't define which of two equal-priority overlapping rules wins. Remove it and add it again with a higher priority:

sh ovs-ofctl --strict del-flows s1 icmp,nw_src=10.NN.0.1,nw_dst=10.NN.0.3
sh ovs-ofctl add-flow s1 priority=40000,icmp,nw_src=10.NN.0.1,nw_dst=10.NN.0.3,actions=drop
h1 ping -c 3 h3
h1 ping -c 3 h2

Now h1 → h3 is blocked, h1 → h2 still works, and the drop rule's n_packets counts up.

If the first ping to h3 still got a reply

That's real behaviour too: the switch keeps a fast cache of recent forwarding decisions, and it takes a moment to catch up with a new rule. See it with sh ovs-appctl dpctl/dump-flows.

Try h3 ping -c 3 h1 as well: it fails too, even though the rule only mentions traffic towards h3. Work out why before opening the hint.

Show hint

What does a ping need to come back? When h3 pings h1, h1 sends an echo reply — with source 10.NN.0.1 and destination 10.NN.0.3. Check that against the drop rule.

Step 4 — Hand the switch to a controller

Start a simple OpenFlow controller (it runs inside the container, listening on port 6653), clear your rules, and point the switch at it:

sh ovs-vsctl set-controller s1 tcp:127.0.0.1:6653
sh ovs-vsctl show

The controller has installed a priority=0 actions=CONTROLLER table-misstable-missWhat an OpenFlow switch does with a packet that matches no other rule — set by a priority-0 rule with no match fields, often "send to the controller". rule — unknown packets go to the controller — plus one flow per conversation it has seen, each with idle_timeout=60. That's reactive flow installation: the table you wrote by hand in Step 2, built on demand.

Step 5 — Break the control channel

Kill the controller:

sh pkill -f ovs-testcontroller
sh ovs-vsctl list controller

Within a few seconds ovs-vsctl list controller shows is_connected: false — if it still says true, wait and run it again. Then test:

  • h1 → h2 (a conversation the controller already set up): still works — its flows are cached in the switch.
  • h1 → h3 (a new conversation): fails. The table-miss rule sends it to a controller that isn't there.
  • Wait a minute and try h1 → h2 again: once its flows reach their 60-second idle timeout, it fails too.

Step 6 — Fail-mode: secure vs standalone

sh ovs-vsctl set-fail-mode s1 standalone

Wait about 15 seconds, then try h1 ping -c 2 h3 again. It works: in standalone mode, once Open vSwitch decides the controller is gone it falls back to behaving like an ordinary learning switch — like Week 1's bridge. In secure mode it never does.

Think about

Which would you want on a production network — especially for a switch whose job includes enforcing firewall rules like the one in Step 3.
