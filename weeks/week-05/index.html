Coding stays light

You don't need to write P4 fluently in this course. Aim to read it, and to know what each block of a program becomes in the hardware. The architecture is the point.

1 · The problem: fixed silicon

Two weeks of evidence point the same way:

  • Week 3: a fixed-function chip's parser knows a fixed list of headers. A new header means a new chip — a gap of years.
  • Week 4: OpenFlowOpenFlowA protocol that lets a controller install match–action rules (flows) directly into a switch's flow tables. lets software fill the tables, but the fields it can match are a fixed list in the standard. That list grew from about a dozen to about forty, and every addition needed a new standard and new switches.

Both times, the switch decides in advance which protocols exist. The idea of this week turns that around. Protocol independence: the switch has no built-in protocols. The programmer defines which headers exist, how to find them in a packet, and what the tables match on — and the chip runs that at line rateline rateThe full speed of a link. Forwarding at line rate means keeping up with every packet the link can carry, even the smallest ones, back to back..

Two milestones made it real:

  • the RMT paper (2013) — this week's reading — showed that such a chip could match the speed and cost of fixed-function chips;
  • P4 (2014) gave it a language. The name stands for Programming Protocol-independent Packet Processors.

2 · PISA: parser, stages, deparser

The model behind P4 hardware is called PISA, the Protocol-Independent Switch Architecture. It keeps Week 3's pipeline, but makes each part programmable:

  • The parser is a state machine. Each state extracts one header from the packet's bytes, then looks at a field — like Ethernet's type — to choose the next state. Its output is the set of headers it found, each marked valid, plus metadata such as the input port.
  • The match–action stages each have their own table memory — SRAM for exact matches, TCAMTCAMTernary Content-Addressable Memory: hardware that compares a lookup key against every table entry at once, with "don't care" bits. Very fast, but expensive and power-hungry, so tables are small. for ternary and longest-prefix matches, as in Week 3 — and units that can read and rewrite header fields. A packet passes through every stage exactly once.
  • The deparser writes the valid headers back, in a fixed order, in front of the payload. The payload itself is never parsed: a switch only looks at headers.

Real architectures split the stages into an ingress pipeline and an egress pipeline, with the queues between them.

3 · P4: the language, and describing a pipeline

What P4 is

P4 — Programming Protocol-independent Packet Processors — is a language for describing how a network device processes packets: which headers it understands, how it pulls them apart, what it looks up, what it changes, and what it puts back on the wire. It was proposed in 2014 by a group that included several authors of this week's reading, to give pipelines like the PISA one you've just seen a language of their own. The current version, P4₁₆, dates from 2017, and the language is developed in the open by the P4 community at p4.org.

The 2014 paper set three goals, and they explain most of the language's design:

  • Reconfigurability — a device's behaviour can be changed after it has been deployed, by loading a new program.
  • Protocol independence — the device has no built-in idea of Ethernet or IPv4. The program defines every header, including ones no standard has ever heard of.
  • Target independence — the same language describes processing on very different devices. A compiler for each target turns the program into what that device runs.

Those targets include software switches such as BMv2BMv2The P4 reference software switch (behavioral model version 2), for running P4 programs without hardware. (the one in this week's lab), programmable switch chips such as Intel's Tofino, SmartNICs and DPUs in servers, FPGAs, and the Linux kernel's own fast path. Each target offers an architecture — the blocks a program fills in, and the metadata it can use. This week's lab uses BMv2's v1model architecture: that's where standard_metadata and mark_to_drop come from.

How P4 differs from the languages you know

P4's syntax looks like C, but it's a different kind of language. Everything below follows from one fact: a P4 program has to run on every packet, at line rate, on hardware with a fixed number of stages (Part 5 shows why).

C, Java, PythonP4
What a program isInstructions for a computer to follow, start to finishA description of a packet-processing pipeline, run once for every packet that arrives
Loops and recursionAnything you likeNone in the match–action code; the parser's state machine is the only place that steps through a sequence (Part 5 explains why)
MemoryAllocate as much as you need; pointers, lists, objectsNo allocation, no pointers. Fixed headers, fixed-size tables, and a few explicit stateful objects (registers, counters, meters)
NumbersIntegers and floating point, of fixed common sizesBit-fields of exact widths — bit<9>, bit<48> — with no floating point. Arithmetic wraps around at the field's width, as in hardware
Where decisions liveIn the codeSplit: the program declares the tables and the actions they may run; the entries — which address goes where — are filled in at run time by the control planecontrol planeThe part of a network that decides how traffic should be forwarded — routing protocols or an SDN controller — and fills in the data plane's tables.
Where it runsOn a general-purpose processor, anywhereOn a specific target and architecture; the same program may fit one device and not another
"It compiles"The code is validThe code is valid and it fits the target: stages, memory, the parser's limits. The compiler refuses a program that wouldn't run at line rate

Two comparisons with things you've met:

  • OpenFlow (Week 4) fills in the tables of a pipeline whose headers and stages are fixed by the chip. P4 defines the pipeline itself — and then something like P4Runtime (Part 4) fills its tables, much as OpenFlow did.
  • A routing protocol or a web server can't be written in P4. Anything that needs loops, large memory or a conversation with other devices belongs in the control plane, written in an ordinary language. P4 handles what happens to each packet; the rest of the system decides what it should be.

Describing a pipeline

A P4 program describes a pipeline: its headers, its parser, its tables and actions, and its deparser. Here's the shape of a small program, piece by piece (shortened from the P4 tutorials' tunnelling exercise).

Headers — just layouts of named bit fields:

header ethernet_t {
    bit<48> dstAddr;
    bit<48> srcAddr;
    bit<16> etherType;
}

header myTunnel_t {
    bit<16> proto_id;   // what comes next, like etherType
    bit<16> dst_id;     // which tunnel exit to send it to
}

The parser — the state machine you just stepped through:

state start {
    packet.extract(hdr.ethernet);
    transition select(hdr.ethernet.etherType) {
        0x1212: parse_myTunnel;
        0x0800: parse_ipv4;
        default: accept;
    }
}

A table and its actions — the match–action part. The program declares what the table matches on and which actions it may run; the entries come later:

action ipv4_forward(macAddr_t dstAddr, egressSpec_t port) {
    standard_metadata.egress_spec = port;
    hdr.ethernet.srcAddr = hdr.ethernet.dstAddr;
    hdr.ethernet.dstAddr = dstAddr;
    hdr.ipv4.ttl = hdr.ipv4.ttl - 1;
}

table ipv4_lpm {
    key = { hdr.ipv4.dstAddr: lpm; }
    actions = { ipv4_forward; drop; }
    size = 1024;
    default_action = drop();
}

That action is Week 3's modify stage, written out: set the output port, rewrite the MACs, decrement the TTLTTLTime To Live: a counter in every IP packet that each router decreases by one. At zero the packet is discarded, which stops packets looping forever..

The deparser — which headers go back into the packet, in order:

packet.emit(hdr.ethernet);
packet.emit(hdr.myTunnel);   // only written if it's valid
packet.emit(hdr.ipv4);

Adding a header touches all three parts, and they have to agree. Every combination below compiles — the mistakes only show in what the packets do. This is the lesson of this week's lab:

5 · Constraints from silicon

P4 looks restrictive at first. Every restriction comes from Week 3's time budget: at line rate, the next packet arrives within nanoseconds, so every packet must flow through the pipeline in a fixed, bounded time.

  • No general-purpose loops. A loop with no known bound might never finish. (Parsers can loop over a header stack, such as MPLS labels, but only to a fixed depth.)
  • A fixed number of stages. Commercial chips have on the order of ten to twenty per pipeline. A packet visits each one once — it can't go back.
  • Fixed memory per stage. Every table must fit somewhere, and TCAM is as scarce as ever.
  • Dependencies cost stages. A table that matches on another table's result must sit in a later stage.

The compiler's job is to fit the program onto the pipeline — and to refuse when it can't. Try it:

These constraints aren't a weakness of P4. They're the honest shape of fast hardware. A fixed-function chip has the same limits — they were just chosen for you, years ago.

6 · What it makes possible

With a programmable data plane, a switch can do things no fixed chip was built for. The best-known example is In-band Network Telemetry (INT): switches write their own measurements into the packets they forward.

INT needs a new header, a parser that knows it, actions that write switch state — queue depth, timestamps — into it at line rate, and a deparser that emits it. That's exactly what PISA provides, and what a fixed chip can't do. The same flexibility lets operators add custom tunnel headers, new load-balancing schemes or fast failover without waiting for new silicon.

Where P4 runs today

The best-known P4 switch chip, Intel's Tofino (originally from Barefoot Networks), is no longer being developed: Intel stopped new generations in 2023. P4 lives on in software switches — BMv2, used for learning, is one — in programmable network cards (SmartNICs and DPUs), and in research. The PISA model, compile-time vs run-time programming and the silicon constraints are the lasting lessons, whatever chip runs them.

Wrap-up

Key takeaways

  • Fixed-function chips and OpenFlow both fix the protocols in advance. Protocol independence lets the program define them.
  • PISA is a programmable parser, a pipeline of match–action stages, and a deparser. The payload is never parsed.
  • A P4 program describes a pipeline: headers, parser, tables and actions, deparser. A new header only works when all of them agree.
  • The program fixes the structure at compile time; table entries are written at run time, for example with P4Runtime.
  • No loops, a fixed number of stages and limited memory per stage all come from the line-rate time budget. The compiler refuses programs that don't fit.
  • Programmable data planes enable things fixed chips can't do, such as In-band Network Telemetry.

Step 3 — Change a table while it runs

List s2's IPv4 table, with each entry's handle:

sh ./p4cli s2 table_dump MyIngress.ipv4_lpm

Delete the entry for h3 (handle 2) and ping it:

sh ./p4cli s2 table_delete MyIngress.ipv4_lpm 2
h1 ping -c 2 -W 1 h3

The ping fails: s2's lookup misses and the default action, drop, runs. Put the entry back:

sh ./p4cli s2 "table_add MyIngress.ipv4_lpm MyIngress.ipv4_forward 10.NN.0.3/32 => 3"
h1 ping -c 2 h3

Keep the quotes: without them, the shell reads the > in => as "send the output to a file".

You changed the switch's behaviour without touching the program: that's run time. A new kind of header needs the program itself changed and recompiled: compile time. That's next.

One more test before you leave. The test packet below is addressed to h3 by IP, but to tunnel exit 2 (h2). If the switches forward by the tunnel header, it reaches h2; if they forward by IPv4, it reaches h3:

h1 python3 send.py 10.NN.0.3 "test 1" --tunnel 2
sh cat logs/h2.txt logs/h3.txt

It reaches neither. In logs/s1.txt, search for key is 1212: the parser read Ethernet, didn't recognise type 0x1212, and stopped. With no valid IPv4 header, the ingress dropped the packet. Type exit.

Step 4 — Teach the parser and the deparser the new header

Edit tunnel.p4 at the three TODO (Step 4) comments. In the parser's start state, add a line to the select:

TYPE_MYTUNNEL: parse_myTunnel;

Add the new state where the second TODO is:

state parse_myTunnel {
    packet.extract(hdr.myTunnel);
    transition select(hdr.myTunnel.proto_id) {
        TYPE_IPV4: parse_ipv4;
        default: accept;
    }
}

And in the deparser, between the Ethernet and IPv4 lines:

packet.emit(hdr.myTunnel);

Save, start the network again and send the same packet:

python3 topo.py --id NNNN

h1 python3 send.py 10.NN.0.3 "test 2" --tunnel 2
sh cat logs/h2.txt logs/h3.txt

It arrives — at h3, still tunnelled, with TTL 62. The switches now understand the header and write it back out, but the forwarding decision still comes from IPv4. And the compiler still says myTunnel_exact is unused. Type exit.

Step 5 — Use the tunnel table

Replace the TODO (Step 5) comment and the if line below it, so that the ingress apply block reads:

apply {
    if (hdr.myTunnel.isValid()) {
        myTunnel_exact.apply();
    } else if (hdr.ipv4.isValid()) {
        ipv4_lpm.apply();
    } else {
        drop();
    }
}

Start the network again. This time there's no warning, and topo.py loads all six entries into each switch. Send the packet:

h1 python3 send.py 10.NN.0.3 "test 3" --tunnel 2
sh cat logs/h2.txt logs/h3.txt

It arrives at h2, with TTL 64. Plain IPv4 still works too: try h1 ping -c 2 h3. Parser, ingress and deparser finally agree. Type exit.

Step 6 — Break it on purpose

Comment out the line you added to the deparser:

// packet.emit(hdr.myTunnel);

Start the network, send the packet as "test 4", and check both hosts. Nothing arrives — and the compiler didn't complain. Find out why from the logs:

  • In logs/s1.txt, search for key is 1212. s1 parsed the packet, looked up dst_id 2 and sent it out of port 2. All correct.
  • In logs/s2.txt, find the same packet arriving. Look at the line Parser state 'parse_myTunnel': key is … and at the dst_id that s2 looked up.

Work out where those two numbers came from before you open the hint.

Show hint

s1 extracted the tunnel header but never wrote it back, so it left with the tunnel header missing — but its Ethernet type still says 0x1212. s2 therefore reads the first 4 bytes of the IPv4 header as a tunnel header. proto_id comes out as 4500: IPv4's version, header length and type-of-service bytes. dst_id comes out as 0022: the IPv4 total length, 34 bytes (20 for IPv4, 8 for UDP, 6 for "test 4"). No tunnel exit 34 exists, so the lookup misses and the packet is dropped. Every part compiled; only the packets show the mistake.

Put the line back, then type exit.

C1 — Analyse: make a tunnel loop

Start the network (python3 topo.py --id NNNN). Re-point tunnel exit 3 on s2 so it sends packets back to s1 (port 1). s1 already sends exit 3 towards s2, so the two switches will pass the packet back and forth:

sh ./p4cli s2 table_dump MyIngress.myTunnel_exact

Find the handle of the entry for key 3, then change its port to 1:

sh ./p4cli s2 "table_modify MyIngress.myTunnel_exact MyIngress.myTunnel_forward <handle> 1"
h1 python3 send.py 10.NN.0.3 "loop" --tunnel 3
sh grep -c "Processing packet received" logs/s1.txt logs/s2.txt
sh sleep 5; grep -c "Processing packet received" logs/s1.txt logs/s2.txt

Each count is how many packets that switch has handled. Save the commands and their output in assignment/evidence/loop-before.txt, and type exit — this loop never stops by itself.

Then look at the IPv4 path in tunnel.p4. ipv4_forward decrements the TTL: does that stop an IPv4 loop in this program? Read the code carefully before you answer in your report.

C2 — Design a hop limit

Change the tunnel header so it carries a hop limit: how many more switches the packet may cross. Decide, and justify in your report:

  • the field's size and where in the header it goes;
  • the starting value the sender uses;
  • where in the pipeline it's decremented, and what happens when it runs out.

C3 — Implement it

Change tunnel.p4 — the header and the ingress logic — and send.py and receive.py: the hosts must agree with the switches about the header, as Step 6 showed. Make send.py able to set the starting value (for example a --hops option) and receive.py print the value that arrives.

Run it often: python3 topo.py --id NNNN compiles your program and tells you at once if something's wrong.

C5 — Evaluate: a mixed rollout

On a real network you can't upgrade every switch at the same moment. Run s1 with your new program and s2 with the old one:

python3 topo.py --id NNNN --s2-program tunnel_v1.p4

Before you send anything, write down your prediction in the report: what will s2 make of your new header? Then send a tunnelled packet to h2, and repeat the loop. Save what you see in assignment/evidence/mixed.txt. If something surprises you, find out why: logs/s2.txt shows what s2 parsed, and this captures the bytes that actually reach h2:

h1 python3 send.py 10.NN.0.3 "mixed" --tunnel 2
sh sleep 8; cat logs/h2cap.txt
