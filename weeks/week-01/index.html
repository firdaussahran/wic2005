1 · A change at 2 a.m.

It's Friday evening. The security team has found that the SNMPSNMPSimple Network Management Protocol: the older, polling-based way to read counters and state from devices. community string — effectively the password for reading device statistics — has leaked. It has to be changed on all 40 switches in the faculty network tonight, in the maintenance window.

The box-by-box way

For each switch, an engineer logs in, changes two lines, checks, and saves:

ssh admin@sw01
sw01# configure terminal
sw01(config)# no snmp-server community OldSecret RO
sw01(config)# snmp-server community N3wSecret RO
sw01(config)# end
sw01# copy running-config startup-config

Then sw02. Then sw03. Each one takes a few minutes if nothing goes wrong — and 40 of them take most of the night. Try the numbers yourself:

Model: by hand = devices × minutes; automated = setup + 0.5 min per device to push and verify. Mistake chance assumes independent errors per device.

Four problems that don't go away

Time is the obvious cost, but it isn't the deepest one. Box-by-box operation has four structural problems:

  1. Human error compounds. Even a 1% chance of a mistake per device means a 1 − 0.99⁴⁰ ≈ 33% chance that at least one of 40 switches ends up wrong. And every mistake is different, so each one has to be found separately.
  2. Configuration drifts. Over months, one-off hand edits make "identical" switches quietly different. Eventually each device is the only record of its own configuration.
  3. There are no transactions. Every CLI line takes effect the moment it's typed. If something fails part-way through, you're left in a state nobody planned — and there's no undo.
  4. There's no abstraction. The intent is one sentence — "rotate the SNMP secret" — but you have to express it as vendor-specific commands, one device at a time.

Quick check

Your script pushes a change to 40 switches over SSH, one at a time. It times out on switch 23 and stops. With ordinary CLI changes — no transactions — what state is the network in?

Think about

Automation clearly fixes the time and the random typos. Which problem does it make worse?

Show the answer

A wrong change now reaches every device at once. By hand, a mistake hits one switch; in a template, it hits all 40 in seconds. That's the blast radiusblast radiusHow much of the network one mistake or one compromise can affect. Automation makes it large by default; guardrails make it small. of automation — Week 12 is about the guardrails that contain it.

2 · Inside a router: three planes

Before we can talk about programming a network, we need to be precise about what's inside a network device. Every router or switch does three different jobs, at very different speeds, often on different hardware:

  • The data planedata planeThe part of a network device that forwards packets, at full speed, using tables it has been given. forwards every single packet — in nanoseconds, in dedicated chips.
  • The control planecontrol planeThe part of a network that decides how traffic should be forwarded — routing protocols or an SDN controller — and fills in the data plane's tables. decides where packets should go — routing protocols recompute paths in milliseconds to seconds.
  • The management planemanagement planeHow people and tools configure and monitor devices: the CLI, SNMP, NETCONF, APIs and so on. is how people and tools configure and monitor the device — on human timescales.

There isn't one: the Week 1 bridge learns MAC addresses by itself, in the data plane.

An analogy: at an airport, the baggage conveyors move every bag (data plane), the routing desk decides which conveyor each flight's bags go to (control plane), and airport management sets the rules and staffs the desks (management plane). The conveyors keep running even while the desk replans.

Why the split matters

In a traditional router, all three planes come bundled in one box, from one vendor, behind a CLI. You can configure the control plane — choose OSPF areas, set BGP policy — but you can't replace it. You can't change what the data plane is able to match on. And the management interface was designed for a human typing.

Each kind of programmability in the next part opens up one of these planes. The split has another consequence that will matter in Week 4: the planes can fail independently. In many designs, if the control plane crashes, the data plane keeps forwarding with the last table it was given — for a while.

Quick check

A link fails. OSPF notices, recalculates the best paths and updates the forwarding table. Which plane does the recalculation happen in?

3 · What "programmable" really means

"Programmable networking" is used for four quite different things. Mixing them up is the most common confusion in the field, and the distinction runs through this whole course.

(a) A programmable data plane

You change how packets are processed: which headers the device understands, what it matches on, and what it does to each packet. A P4P4A language for describing how a programmable switch parses and processes packets. program can teach a switch a header that didn't exist when the chip was made — something fixed-function silicon can't do. Week 5.

(b) An externalised control plane

You move the decisions about where traffic goes out of each box into software with a view of the whole network — a logically centralised controller. The devices follow its instructions. OpenFlowOpenFlowA protocol that lets a controller install match–action rules (flows) directly into a switch's flow tables. and Google's B4 WAN are the classic examples. Week 4.

(c) Programmatic device interfaces

You change how you talk to devices: structured data through APIsAPIApplication Programming Interface: a defined way for programs to talk to a system — for example, a controller's REST API., defined by schemas, instead of CLI text written for humans. NETCONFNETCONFA network management protocol, usually over SSH, that exchanges YANG-modelled data as XML and supports transactions: candidate datastore, commit and locking., RESTCONFRESTCONFAn HTTP-based protocol that exposes YANG-modelled data as REST resources, in JSON or XML. and gNMIgNMIgRPC Network Management Interface: gets, sets and streams YANG-modelled data over gRPC, using protobuf encoding., carrying YANG-modelled data. Weeks 7–9.

(d) Automated configuration management

You change how configuration is produced and applied: generated from a source of truthsource of truthThe authoritative record of how the network should be — usually data in Git, or a tool such as NetBox. Devices are configured from it, never the other way round., reviewed, tested and pushed to many devices repeatably. AnsibleAnsibleAn agentless automation tool: playbooks describe the desired state, and modules apply it to devices over SSH or APIs., Jinja2Jinja2A Python templating language, used here to render device configurations from data. templates, GitGitA version control system that records every change to a set of files as a commit, so you can see, compare and undo changes. and CI pipelines. Common confusions

  • "SDN" gets used for all four. In this course, SDN means (b): control moved out of the devices.
  • Automation isn't the same as APIs. A script that types CLI commands is (d) without (c) — and it breaks whenever the output format changes.
  • They combine. A real network might use Ansible (d) talking NETCONF (c) to devices whose forwarding is steered by a controller (b).

4 · How we got here

None of these ideas is new. The field is three decades of attempts to open up one plane or another — each solving a real problem, and each running into limits. Step through the history:

Explore: how we got here

mid-1990s – early 2000s

Active networks

The idea
Make the network itself programmable: packets ("capsules") could carry code for routers to run, or operators could load new programs into network nodes.
What it left us
The ambition of a programmable data plane — revived, far more safely and narrowly, by P4.
Why it wasn't the end of the story
No compelling application at the time, and serious concerns about the safety and performance of running arbitrary code inside routers.
1 of 7

Three lessons from the history

  1. Deployability beats elegance. Ideas that worked with existing hardware — OpenFlow on commercial switches, NETCONF on existing routers — spread. Clean-slate designs mostly didn't.
  2. Separating the planes was the enabling idea. Once control is separate from forwarding, it can be moved, replaced or programmed.
  3. The hype moved on; the ideas stayed. Few campus networks run pure OpenFlow today, but model-driven APIs and automation are everyday operations. Week 12 comes back to this honestly.

Wrap-up

Key takeaways

  • Box-by-box CLI breaks at scale: errors compound, configurations drift, and there are no transactions and no abstraction.
  • Every network device does three jobs — data, control and management — at very different speeds.
  • "Programmable" means four different things: a programmable data plane, an externalised control plane, programmatic device interfaces, and automated configuration management. Always say which one you mean.
  • They solve different problems, and real networks combine them.
  • The history is a series of attempts to open up one plane or another; the ideas that lasted were the deployable ones.

Lab

Goal

Build your first network and watch Ethernet work on its own — no controller, no configuration. A switch that learns by itself is the baseline that everything else in this course changes.

This lab is short and relaxed. There's nothing to hand in; just explore.

Before the lab

Install DockerDockerA tool for packaging and running software in containers: isolated processes with their own filesystem and network namespace. Desktop (macOS or Windows) or Docker Engine (Linux), start it, and check it works:

docker run hello-world

That's the only thing to install. Labs in Weeks 1–6 all run inside one course container that already has everything else.

Step 1 — Start the lab container

In a terminal (macOS Terminal, Windows PowerShell or a Linux shell):

docker run -it --rm --privileged -v "${PWD}:/lab" -w /lab firdaussahran/netlab-mininet:1.0

The first time, this downloads the course image (about 265 MB). You end up at a prompt inside the container. What the options mean:

  • --privileged lets MininetMininetA tool that emulates a network of hosts, switches and links on one Linux machine, using network namespaces. create virtual network cables and switches.
  • -v "${PWD}:/lab" shares the folder you started in, as /lab inside the container.
  • --rm deletes the container when you exit, so every start is fresh.

Step 2 — Build a network

mn --topo single,3 --mac --switch lxbr --controller none

That's one switch (s1) with three hosts (h1, h2, h3). --mac gives the hosts simple MAC addressesMAC addressThe hardware address of a network interface, such as 00:00:00:00:00:01. Ethernet switches forward frames by MAC address., --switch lxbr makes the switch an ordinary Linux bridgeLinux bridgeA software Ethernet switch built into the Linux kernel. It learns MAC addresses like a hardware switch., and --controller none means nothing controls it. You're ready when you see the mininet> prompt.

Tip

You may see warnings about resource limits and bridge-nf-call. They're harmless — ignore them.

Step 3 — Look around

nodes
net
dump

nodes lists the devices, net shows how they're cabled, and dump shows each host's IP address. Find the line in net's output that matches the cable between s1 and h2 in the diagram above.

Step 4 — Before any traffic

h1 ip neigh
sh brctl showmacs s1

h1 ip neigh is h1's ARPARPAddress Resolution Protocol: how a host finds the MAC address for an IP address on its local network — it broadcasts a request, and caches the reply. table — the IP-to-MAC addresses it knows. It's empty. sh runs a command on the switch's side: brctl showmacs s1 is the switch's MAC table. It only lists the switch's own ports (is local? yes); it knows nothing about the hosts yet.

Step 5 — Send a ping, then look again

h1 ping -c 3 h2
h1 ip neigh
sh brctl showmacs s1

(Mininet replaces h2 with h2's IP address, 10.0.0.2.) Now h1's ARP table maps 10.0.0.2 to 00:00:00:00:00:02: before it could send the ping, h1 broadcast "who has 10.0.0.2?" and h2 answered. The switch's table now has 00:00:00:00:00:01 on port 1 and 00:00:00:00:00:02 on port 2 — it learned where each host is from the frames passing through. Notice that h3 isn't listed. Why not?

Show answer

h3 hasn't sent a single frame yet. A switch learns a MAC address from the source of each frame it receives, so a host that has stayed silent is unknown to it.

Then test everything at once:

pingall

Step 6 — Break a link

link s1 h3 down
pingall
link s1 h3 up
pingall

With the cable to h3 down, every ping to or from h3 fails (shown as X). Bring it back up and the network recovers by itself.

Step 7 — A web server on your network

h2 python3 -m http.server 80 &
h1 curl h2

h2 is now a web server, and h1 just downloaded a page from it across your network. When you're done, type exit to leave Mininet, then exit again to leave the container.

Troubleshooting

Find your symptom, apply the fix, move on.

"Cannot connect to the Docker daemon"

Cause: Docker is installed but not running.

Fix:

  • macOS / Windows: open the Docker Desktop application and wait until it says Docker is running.
  • Linux: run sudo systemctl start docker, then sudo systemctl enable docker so it starts automatically next time.
  • Confirm with docker run hello-world.

docker: permission denied on Linux

Cause: your user account isn't in the docker group, so every Docker command needs sudo.

Fix: run sudo usermod -aG docker $USER, then log out and back in. Until then, prefix Docker commands with sudo.

Windows: Docker Desktop won't start, or mentions WSL 2

Cause: Docker Desktop on Windows runs on WSL 2, which needs to be enabled separately.

Fix:

  1. Open PowerShell as Administrator, run wsl --install, and restart when prompted.
  2. Open Docker Desktop again.
  3. If it still fails, make sure virtualisation is enabled in your BIOS/UEFI settings.

The first docker run takes a long time

Cause: it's downloading the course image (about 265 MB) — normal, and only the first time. Occasionally it's a network block.

Fix: give it a few minutes. If it fails or stalls for more than 10 minutes, check Docker has internet access with docker run alpine ping -c 3 8.8.8.8; if that fails, try a different network (some campus Wi-Fi blocks Docker downloads).

mn stops at *** Adding hosts: and never continues

Cause: the container was started without --privileged, so Mininet isn't allowed to create network devices.

Fix: press Ctrl+C, type exit, and start the container again with the full command from Step 1.

Mininet crashed, and now mn fails with "File exists" errors

Cause: a previous run left virtual devices behind.

Fix: run mn -c to clean up, then start mn again. Or simply exit the container and start a new one — --rm means each one starts clean.

Windows: the Step 1 command fails with an error mentioning ${PWD} or the volume

Cause: the command was typed in the old Command Prompt (cmd.exe), which doesn't understand ${PWD}.

Fix: use PowerShell (or Windows Terminal with PowerShell) instead.

docker run can't download firdaussahran/netlab-mininet

Cause: Docker Hub is blocked on your network, or the download keeps failing.

Fix: build the image yourself instead. Download netlab-mininet.Dockerfile into an empty folder and, from that folder, run:

docker build -t firdaussahran/netlab-mininet:1.0 -f netlab-mininet.Dockerfile .

It takes a few minutes (it still needs internet for Ubuntu packages). Afterwards the Step 1 command uses your local copy.

General rule if none of the above matches

Copy the exact error message (not a paraphrase) and bring it to the lab session or post it in the course forum. Screenshots of the whole terminal, not just the error line, help a demonstrator diagnose it in seconds rather than minutes.
