Why this week matters

If one idea ties the course together, it's this one: the network has a schema. Once that clicks, everything after it — NETCONFNETCONFA network management protocol, usually over SSH, that exchanges YANG-modelled data as XML and supports transactions: candidate datastore, commit and locking., RESTCONFRESTCONFAn HTTP-based protocol that exposes YANG-modelled data as REST resources, in JSON or XML., gNMIgNMIgRPC Network Management Interface: gets, sets and streams YANG-modelled data over gRPC, using protobuf encoding., AnsibleAnsibleAn agentless automation tool: playbooks describe the desired state, and modules apply it to devices over SSH or APIs., intent — is transport and tooling around the same models.

1 · The network has a schema

Last week, the VLAN APIAPIApplication Programming Interface: a defined way for programs to talk to a system — for example, a controller's REST API. rejected VLAN 5000 with a 422. So where is the rule "a VLAN ID is 1 to 4094" written down? In Week 2 you wrote your own check() for duplicate IP addresses — and every script that touches that data would need to write it again.

A schema states, once and in a form programs can read, what data is allowed: its structure, its types, its ranges, which values must refer to which. Then the device and every client can check data the same way, before anything is applied. YANG is the schema language for networks: first standardised in 2010, and as YANG 1.1 in 2016.

YANG doesn't carry data. It's Week 2's data model, written down precisely. The same YANG-modelled data travels as XML over NETCONF, as JSON over RESTCONF, or as protobufprotobufProtocol Buffers: a compact binary encoding for structured data, defined by a schema. Smaller and faster to parse than JSON or XML. over gNMI — next week's three protocols.

2 · Reading a YANG module

The module header

Every module starts the same way. This is the top of this week's example module:

module example-vlans {
  yang-version 1.1;
  namespace "urn:example:vlans";   // makes its names globally unique
  prefix vl;                        // short name used inside the module

  description
    "VLANs, and the switch ports that carry them.";

  revision 2026-11-27 {             // one dated entry per version
    description
      "Initial revision.";
  }
  // ... typedefs and data nodes follow
}

The namespace keeps two modules' name leaves from colliding; the prefix is its short form. Each revision records a dated version (Part 6). A module that needs another module's definitions imports it — import ietf-inet-types { prefix inet; } — and then writes inet:ipv4-address.

The building blocks

The data itself is built from a handful of statements:

  • container — groups related nodes, like a folder;
  • list — many entries of the same shape, each identified by a unique key;
  • leaf — a single value with a type;
  • leaf-list — many values of one simple type;
  • typedef — a named, reusable type, defined once.

Two more you'll meet in real models: grouping/uses to reuse a block of nodes, and augment to add nodes into someone else's module. A choice with cases says "exactly one of these alternatives", such as a port that is either access (one VLAN) or trunk (many).

Types

Every leaf has a type. The built-in ones cover most needs:

TypeHoldsExample
int8 … int64, uint8 … uint64Whole numbers of a fixed sizeuint16 for a VLAN ID
decimal64Decimals, with set precisionA threshold of 0.75
stringTextA VLAN name
booleantrue or falseenabled
enumerationOne of a fixed list of namesdata, voice, management

Common types aren't redefined in every module: ietf-inet-types and ietf-yang-types (RFC 9911, Common YANG Data Types) provide ipv4-address, ip-prefix, mac-address, counter64 and more, through import.

Real modules run to thousands of lines, so engineers read them as trees, generated by pyang -f tree. Here's this week's example module — VLANs and the switch ports that carry them, continuing Week 7's VLAN API — both ways. Click any line of the tree:

A leaf holds one value. Its type, vlan-id, is a typedef defined once at the top of the module: a uint16 restricted to 1..4094. That's where Week 7's VLAN 5000 was rejected.

example-vlans.yang

module example-vlans {  yang-version 1.1;  namespace "urn:example:vlans";  prefix vl;   description    "VLANs, and the switch ports that carry them.";   revision 2026-11-27 {    description      "Initial revision.";  }   typedef vlan-id {    type uint16 {      range "1..4094";    }    description      "An IEEE 802.1Q VLAN ID.";  }   container vlans {    list vlan {      key "id";      must "not(purpose = 'voice') or qos-priority" {        error-message "A voice VLAN needs a qos-priority.";      }      leaf id {        type vlan-id;      }      leaf name {        type string {          length "1..32";          pattern '[a-z][a-z0-9-]*';        }        mandatory true;      }      leaf purpose {        type enumeration {          enum data;          enum voice;          enum management;        }        default "data";      }      leaf qos-priority {        type uint8 {          range "0..7";        }      }      leaf member-count {        config false;        type uint32;        description          "How many ports currently carry this VLAN.";      }    }  }   container ports {    list port {      key "name";      leaf name {        type string;      }      leaf enabled {        type boolean;        default "true";      }      leaf access-vlan {        type leafref {          path "/vl:vlans/vl:vlan/vl:id";        }      }      leaf-list trunk-vlans {        type vlan-id;      }      leaf oper-status {        config false;        type enumeration {          enum up;          enum down;        }      }    }  }}

rw = configuration · ro = state · * = list or leaf-list · [key] · ? = optional · -> = leafref. RESTCONF URLs are next week’s topic.

Every node has a path. /vlans/vlan[id='20']/name picks one leaf out of the whole tree, and a RESTCONF URL is just that path in URL form. That's why a model, once you can read it, tells you exactly how to reach any piece of configuration.

3 · Rules the data must obey

Types are only the start. YANG lets a model say precisely which values make sense:

StatementIn example-vlansRejects
rangeuint16 { range "1..4094"; }, via the vlan-id typedefVLAN 5000
lengthlength "1..32" on the nameA 33-character name
patternpattern '[a-z][a-z0-9-]*' on the name"Guest WiFi"
enumerationdata, voice or management"video"
mandatorymandatory true on the nameA VLAN with no name
mustnot(purpose = 'voice') or qos-priorityA voice VLAN without a QoS priority
leafrefaccess-vlan must be an existing VLAN's idA port in VLAN 30, when there is no VLAN 30

Two more you'll see elsewhere: when makes a node exist only under a condition, and unique makes a set of leaves unique across a list's entries. Patterns always have to match the whole value.

must is code — test it

This module's must rule was first written as purpose != 'voice' or qos-priority. Testing it with yanglint showed the flaw: in XPath, comparing a missing node with != is false, so before defaults were applied, VLANs that weren't voice VLANs were rejected too. not(purpose = 'voice') says what was meant. Rules in a model are logic, and logic needs tests.

4 · Configuration, state and datastores

Every node in a model is one of two kinds, marked rw or ro in the tree:

  • configuration (config true) — what you want: a port enabled, a VLAN named;
  • state (config false) — what's actually happening, reported by the device: a port's oper-status, a VLAN's member count, counters, learned routes. You can read state, but never set it.

Where does each live? The NMDA (Network Management Datastore Architecture, 2018) organises a device's data into datastores:

DatastoreWhat it holds
<candidate>A scratchpad copy of the configuration. Edit freely; nothing happens until you commit
<running>The configuration the device is using now
<startup>The configuration loaded at boot, on devices that keep one separately
<intended>Running, after the device removes inactive parts and expands templates: what it will try to apply
<operational>Everything actually in effect: applied configuration, configuration the system created itself, and all state

Follow one change through them:

  • vlan 10 users
  • vlan 20 voice qos 5

<operational>

  • vlan 1 default [origin: system]

5 · Whose model?

There's no single YANG model of an interface. There are three families, and real networks use all of them:

Native (vendor)IETFOpenConfig
Written byEach vendor, for its own platformsThe IETF standards processA group of network operators
CoverageEverything the platform can doThe common basicsBroad, operator-driven, but each vendor supports a subset
PortabilityOne vendor onlyHighHigh, across the vendors that support it
ChangesWith every software releaseSlowlyRegularly, with semantic versions

Here's the same leaf — an interface's description — in each family:

Compare: one interface description, four models

ietf-interfaces (RFC 8343), from the standards body

Path to the description

/ietf-interfaces:interfaces/interface[name='GigabitEthernet1']/description

module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name           string
        +--rw description?   string
        +--rw type           identityref
        +--rw enabled?       boolean
        +--ro oper-status    enumeration
Good
Standard, stable, and implemented by many vendors.
The catch
Deliberately minimal: the basics only. Anything richer comes from other modules that augment it.

Trees trimmed to the nodes that matter here; real ones are far larger.

That's the real-world tension. Native models are complete but lock your automation to one vendor. Standard models are portable but cover less, and every vendor supports them a little differently, declared in deviations — statements saying which parts of a model a device doesn't implement. In practice, teams use OpenConfig or IETF models where they cover the need, and native models for the rest.

6 · Models change

Models evolve, and every change is recorded in a new revision statement. YANG's rules separate safe changes from breaking ones:

Backward compatibleBreaks existing clients
Adding an optional leaf or a new containerRemoving or renaming a node
Adding a new enum valueChanging a leaf's type
Widening a range or a lengthNarrowing a range or a length
Adding a whole new moduleMaking an existing leaf mandatory
Clarifying a descriptionChanging a list's key

A breaking change isn't meant to be a new revision at all: it needs a new module. Even "safe" additions deserve care — a client reading data should expect enum values it doesn't know yet.

Wrap-up

Key takeaways

  • The network has a schema. YANG says what data is allowed; JSON, XML and protobuf just carry it.
  • A module is built from containers, lists with keys, leaves, leaf-lists and typedefs, and read as a tree. Every node has a path.
  • Constraints — range, length, pattern, enumeration, mandatory, must, leafref — let every client and device reject bad data before it reaches the network.
  • Configuration is what you want; state is what's happening. NMDA's datastores keep them apart, and comparing intended with operational reveals driftconfiguration driftA difference between what the source of truth says and what a device actually has — from a manual change, a failed run, or a replaced device..
  • Native, IETF and OpenConfig models trade completeness against portability. Real networks use all three.
  • Revisions may only add and widen; anything that breaks clients needs a new module.

Step 1 — Read a real model

ietf-interfaces (RFC 8343) is the standard model of a network interface, implemented by most routers and switches that speak NETCONF or RESTCONFRESTCONFAn HTTP-based protocol that exposes YANG-modelled data as REST resources, in JSON or XML.. Draw its tree:

pyang -f tree $M/ietf/ietf-interfaces.yang

The first lines:

module: ietf-interfaces
  +--rw interfaces
  |  +--rw interface* [name]
  |     +--rw name                        string
  |     +--rw description?                string
  |     +--rw type                        identityref
  |     +--rw enabled?                    boolean
  |     +--rw link-up-down-trap-enable?   enumeration {if-mib}?
  |     +--ro admin-status                enumeration {if-mib}?
  |     +--ro oper-status                 enumeration

Read the whole tree, and note in your lab notes:

  1. What is the list's key? How would you address one interface?
  2. Which nodes can you set, and which can you only read? Find three of each.
  3. type is an identityref. Find where its values come from: grep -n "identity ethernetCsmacd" $M/iana/iana-if-type.yang.
  4. The second half starts with x--ro interfaces-state. x means deprecated. Step 2 — Augment, and finding your way

Where is an interface's IP address? Not in ietf-interfaces: a second module, ietf-ip (RFC 8344), augments it — it adds nodes inside another module's tree. Look at what it adds:

pyang -f tree $M/ietf/ietf-ip.yang | head

Now draw both together, zooming in on one part with --tree-path:

pyang -f tree --tree-path /interfaces/interface/ipv4/address \
      $M/ietf/ietf-interfaces.yang $M/ietf/ietf-ip.yang

module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw ip:ipv4!
           +--rw ip:address* [ip]
              +--rw ip:ip                     inet:ipv4-address-no-zone
              +--rw (ip:subnet)
              |  +--:(ip:prefix-length)
              |  |  +--rw ip:prefix-length?   uint8
              |  +--:(ip:netmask)
              |     +--rw ip:netmask?         yang:dotted-quad {ipv4-non-contiguous-netmasks}?
              +--ro ip:origin?                ip-address-origin
  • ip: marks nodes that come from ietf-ip, the augmenting module.
  • ! marks a presence container: ipv4 existing means something on its own — IPv4 is on.
  • (ip:subnet) is a choice with two cases: give a prefix length or a netmask, never both.
  • {…}? marks a feature that a device may or may not support.

Write down, for your own address 10.NN.1.1/24 on eth1:

  • the path to its prefix length, in the lecture's form: /interfaces/interface[name='eth1']/…. Remember that address is a list too, keyed by ip;
  • the RESTCONF URL for the same leaf. The module's name appears at the top, and again wherever the tree crosses into another module: /restconf/data/ietf-interfaces:interfaces/interface=eth1/ietf-ip:ipv4/….

Step 3 — Check data against a real model

Open interfaces.json and change every 10.7. to your own 10.NN.. It's two interfaces' configuration, in the JSONJSONJavaScript Object Notation: a minimal text format for structured data — objects, arrays, strings, numbers, booleans and null. encoding of the models (RFC 7951). Check it:

IF="$M/ietf/ietf-interfaces.yang $M/ietf/ietf-ip.yang $M/iana/iana-if-type.yang"
yanglint -t config -p $M $IF interfaces.json && echo VALID

No messages, and VALID: the data fits the models. (iana-if-type is listed because the data names identities from it. -t config says the file is configuration — Step 6 shows why that matters.)

Now break it, one change at a time, check again, and undo the change before the next:

  1. a prefix length of 33;
  2. an interface type of iana-if-type:ethernet;
  3. an address of 10.NN.1.300;
  4. remove lo0's name.

For each, note the message and the path yanglint reports. Some mistakes give two messages: the second is often a consequence of the first. Read the first one.

Step 5 — Write your own module

Teras Hub — the mini-project's client — wants its Wi-Fi networks modelled, each carried on a VLAN from example-vlans. Write example-wifi.yang in your week8 folder from this specification:

NodeRules
The moduleexample-wifi, namespace urn:example:wifi, prefix wf, a revision dated today. It imports example-vlans (prefix vl)
wifi → networkA container holding a list of networks, keyed by ssid

module: example-wifi

        +--rw ssid          string
        +--rw vlan          -> /vl:vlans/vlan/id

(yanglint finds example-vlans.yang by itself, because it's in the same folder.) Now write two bad files of your own, each breaking one rule, and show that both are rejected: wifi-bad-1.json, a secured network without a passphrase, and wifi-bad-2.json, a network on a VLAN that doesn't exist. If yours is accepted, your module is missing a rule: that's what the bad files are for.

Step 6 — Configuration or state?

Run these three, and compare:

yanglint -t config example-vlans.yang vlans-state.json
yanglint example-vlans.yang vlans-state.json && echo VALID
yanglint -p $M $IF interfaces.json
  • With -t config, yanglint treats the file as a configuration datastore — what <running> or <candidate> hold. State (config false) can't be there, so vlans-state.json is rejected.
  • Without it, yanglint treats the file as all of a device's data, as in <operational>: configuration and state. Now vlans-state.json is fine, and interfaces.json fails: a device must report oper-status, if-index and the other state leaves the model makes mandatory, and the file has none.

Copy wifi-good.json to wifi-clients.json, add "clients": 12 to one network in the copy, and check the copy both ways. Which datastore would hold your file — and which would hold a device's answer?

Step 7 — Models change

Save the current version, then change the module:

mkdir -p old && cp example-wifi.yang old/

Add a new revision (a later date than your first — tomorrow's will do — at the top of the revisions) and an optional leaf max-clients (uint16). Ask pyang whether the change is safe for existing clients:

pyang -P . --check-update-from old/example-wifi.yang example-wifi.yang && echo COMPATIBLE

(-P . tells pyang where the old version's imports are.) Now try three breaking changes, one at a time, undoing each before the next, and run the check after each:

  1. make passphrase mandatory;
  2. remove hidden;
  3. narrow passphrase to 12 to 63 characters.

Which did pyang catch? Look back at the lecture's table in Part 6: should it have caught all three?
