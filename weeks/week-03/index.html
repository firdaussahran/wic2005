Why this week matters

So far a router has been a box that "forwards packets". This week we open the box. Without it, SDNSDNSoftware-Defined Networking: taking the control plane out of individual switches and running it as software, often on a logically centralised controller. and P4P4A language for describing how a programmable switch parses and processes packets. look like magic. With it, you'll see exactly which parts of the box they make programmable, and why that was hard.

1 · The life of a packet

In Week 1 you split a network device into three planes. This hour is about the data planedata planeThe part of a network device that forwards packets, at full speed, using tables it has been given.: the part that handles every single packet. Whatever the device — a Linux host routing in software, a campus switch, a core router — the same six stages happen, in order:

  1. Ingress — the frame arrives on a port and is checked for damage.
  2. Parse — the headers are identified and the fields that matter are pulled out.
  3. Lookup — those fields are matched against a table to decide where the packet goes.
  4. Modify — the headers are rewritten for the next link.
  5. Queue — the packet waits for the outgoing port to be free.
  6. Egress — the frame is sent out.

2 · Longest-prefix match

The lookup stage is where the decision is made. A router's table doesn't list every address — that would be billions of entries. It lists prefixes: 10.2.0.0/24 means "every address whose first 24 bits are the same as 10.2.0.0's". The other 8 bits can be anything.

Prefixes can overlap. r1, in this week's lab, has both 10.2.0.0/16 and 10.2.0.0/24. Which one does a packet for 10.2.0.10 use? Write everything in binary and compare only the bits each prefix fixes:

10.2.0.10     00001010.00000010.00000000.00001010
10.2.0.0/16   00001010.00000010.********.********   match
10.2.0.0/24   00001010.00000010.00000000.********   match, and longer
10.1.0.0/24   00001010.00000001.00000000.********   no — the second byte differs

Both 10.2 routes match. The rule — longest-prefix match — says the route with the most fixed bits wins, because it's the most specific: it describes a smaller, more precise part of the address space. So 10.2.0.10 goes via the /24.

A default route, 0.0.0.0/0, fixes no bits at all, so it matches every address — and it always loses to anything more specific. That makes it the route of last resort. r1 has none, which is why 8.8.8.8 gets "Network is unreachable".

A router's FIB holds 10.0.0.0/8 via A, 10.2.0.0/16 via B, 10.2.0.0/24 via C and 0.0.0.0/0 via D. Where does it send a packet for 10.2.5.1?

3 · RIB and FIB

Where does the table come from? Two different tables are involved, built by two different planes.

  • The RIB (Routing Information Base) belongs to the control planecontrol planeThe part of a network that decides how traffic should be forwarded — routing protocols or an SDN controller — and fills in the data plane's tables.. It collects every route the router knows from every source: directly connected networks, static routes, OSPF, BGP. Several sources can offer the same prefix; the router picks one by preference (on many routers called administrative distance) and keeps the others as backups.
  • The FIB (Forwarding Information Base) belongs to the data plane. It holds only the winners, already resolved to what forwarding needs: the outgoing port and the next hop's MAC addressMAC addressThe hardware address of a network interface, such as 00:00:00:00:00:01. Ethernet switches forward frames by MAC address.. It's arranged for fast lookup, not for humans to read.
RIBFIB
Built byControl plane: routing protocols and configurationControl plane installs it; data plane uses it

That last row is the one people mix up. Choosing a route source happens once, when the RIB changes. Longest-prefix match happens for every packet, in the FIB.

4 · The time budget

How fast does the lookup have to be? On Ethernet, the smallest frame is 64 bytes, and every frame takes another 20 bytes' worth of wire time. On a 100 Gb/s port that's a new packet every 6.7 nanoseconds — and a switch has dozens of ports. Play with the numbers:

Each Ethernet frame also costs 20 bytes of wire time (preamble and inter-frame gap). 64 bytes is the smallest Ethernet frame: the worst case a device must be designed for. The memory figure is a rough typical value.

At the speeds of a modern switch, the budget per packet is a fraction of a nanosecond for the whole device — less than one clock cycle of a general-purpose CPU, and far less than a single trip to main memory. That's why devices split the work between different kinds of engine:

Your lab routers this week are Linux hosts: software forwarding. The decisions they make are exactly the ones an ASIC makes — only much more slowly.

The punt path is a weak spot

Because the control-plane CPU is so much slower than the forwarding hardware, a flood of packets that must be punted — say, thousands of packets a second with TTL 1 — can overload it, and take the routing protocols down with it. Routers rate-limit traffic to the CPU for exactly this reason. Security is a data-plane question too (Week 12).

5 · TCAM: a lookup in one step

Searching a table entry by entry is out of the question at a fraction of a nanosecond. Hardware routers use special memory instead.

Ordinary memory answers "what's stored at this address?". Content-addressable memory (CAM) answers the opposite: "at which address is this value stored?" — by comparing the value with every row at once, in one step, whatever the table size. A switch's MAC table needs only exact matches. Longest-prefix match needs more: "the first 24 bits must be these; the rest don't matter".

A TCAM — ternary CAM — stores three states per bit: 0, 1, and * (don't care). A prefix is exactly that kind of pattern: 10.2.0.0/16 is 16 fixed bits followed by 16 *s. Every row whose pattern matches raises its match line, and a priority encoder picks the first matching row.

Try it on a toy router with 8-bit addresses — then switch the row order:

All 4 rows were compared with the key at the same moment. The priority encoder picked row 1: port 3. That’s the longest-prefix match, as it should be.

The TCAM knows nothing about prefix lengths — only row order. Routers make the first match the longest match by keeping longer prefixes higher up. Adding one route can mean moving many rows to make room in the right place.

Why TCAM is a scarce resource

That parallel comparison has a price. Each TCAM bit needs its own comparison circuitry — roughly two to three times the transistors of an ordinary memory bit — and every row is switched on for every lookup, so TCAMs burn a lot of power. They're expensive, hot and therefore small: a switch chip might have room for tens of thousands to a few hundred thousand entries, shared between routes, access-control lists and quality-of-service rules. Many chips stretch capacity with clever algorithms in ordinary memory, but the trade-off stays: fast lookup memory is scarce.

Table size is a hard limit, and when it runs out, things break. On 12 August 2014 the global IPv4 routing table passed roughly 512,000 routes. Some widely deployed routers had their hardware tables set up for 512K IPv4 routes by default. They could no longer install every route, and several networks had outages that day. It's now remembered as "512K Day". The full IPv4 table today is close to a million routes, so the same pressure continues.

Quick check

A TCAM returns the first row that matches. A careless driver writes 10.0.0.0/8 into row 1 and 10.2.0.0/16 into row 2. A packet arrives for 10.2.3.4. What happens?

6 · Where features come from

A fixed-function ASIC has a fixed parser — it knows a set list of headers — and fixed tables with fixed purposes. If a header isn't on that list, the chip can't look inside it. All a software update can do is send those packets to the slow CPU.

VXLANVXLANVirtual Extensible LAN: carries Ethernet frames inside UDP packets (port 4789), so a layer-2 network can stretch across a routed IP network. (Week 6) shows the cost. The first VXLAN draft appeared in 2011. Switch chips that could handle it in hardware arrived roughly a year or two later, and the standard itself was published in 2014. Every switch already installed stayed unable to do it at line rate. A new chip takes years to design, and switches stay in service for years after that. The result is a multi-year gap between "we want a new header" and "our network can forward it".

That gap is the problem the next two weeks attack:

  • Week 4 — OpenFlowOpenFlowA protocol that lets a controller install match–action rules (flows) directly into a switch's flow tables. lets software outside the box fill the tables. But the tables and the headers they can match are still the chip's.
  • Week 5 — P4 goes further: a program defines the parser and the pipeline themselves, on chips built to be programmed.

Quick check

A new tunnel header becomes a standard. Your switches use fixed-function ASICs, and you need it at full speed on every port. What's the realistic route?

Wrap-up

Key takeaways

  • Every device forwards in the same stages: ingress, parse, lookup, modify, queue, egress. Ethernet addresses and TTL change at every hop; IP addresses don't.
  • Longest-prefix match picks the most specific matching route — and you can work it out in binary.
  • The control plane builds the RIB and chooses between sources. The data plane uses the FIB, and LPM chooses between prefixes for every packet.
  • At line rate there are only nanoseconds per packet. That's why the fast path is hardware and the CPU only handles exceptions.
  • A TCAM matches every row at once, but it's expensive, power-hungry and small. Table size is a first-order design constraint.
  • Fixed-function silicon decides which headers and features exist. Changing that takes years — the motivation for Weeks 4 and 5.

Before next week

If someone could write any rule they liked into a switch's tables, from outside the switch, what would you want to be able to match on — and what would you do with the packets? Keep your answer: it's the starting point for OpenFlow.

Further reading

  • Varghese, Network Algorithmics (Morgan Kaufmann) — its chapter on prefix lookups covers tries, TCAMs and the trade-offs between them.
  • Bosshart et al., "Forwarding Metamorphosis: Fast Programmable Match-Action Processing in Hardware for SDN" (SIGCOMM 2013) — the paper behind programmable switch pipelines, and the bridge to Week 5.

Tip

Write down what you see at each step — your write-up is built from your observations.

Step 1 — What works before routing

h1 ping -c 2 10.NN.1.1
h1 ping -c 2 10.NN.32.10

h1 can reach its own gateway (r1) but not h2.

Step 2 — Read the routers' tables

r1 ip route
r2 ip route
r1 sysctl net.ipv4.ip_forward

Each router only has proto kernel routes: networks on its own interfaces. And ip_forward = 0 means r1 won't pass packets between interfaces at all.

Step 3 — Switch forwarding on

r1 sysctl -w net.ipv4.ip_forward=1
r2 sysctl -w net.ipv4.ip_forward=1
r3 sysctl -w net.ipv4.ip_forward=1
h1 ping -c 2 10.NN.32.10

Still no reply, but the error has changed: r1 now answers Destination Net Unreachable. It's willing to forward, but it has no route to 10.NN.32.10.

Step 4 — Add static routes

Give r1 two overlapping routes towards h2's and h3's networks: a specific /24 for h2's network straight to r2, and a broad /20 via r3 that covers 10.NN.32.0 to 10.NN.47.255 — both LANs and more. Then give r3 and r2 what they need:

r1 ip route add 10.NN.32.0/24 via 10.NN.12.2
r1 ip route add 10.NN.32.0/20 via 10.NN.13.2
r3 ip route add 10.NN.32.0/20 via 10.NN.23.2
r3 ip route add 10.NN.1.0/24 via 10.NN.13.1
r2 ip route add 10.NN.1.0/24 via 10.NN.12.1

Now h1 ping -c 2 10.NN.32.10 (h2) and h1 ping -c 2 10.NN.33.10 (h3) both work.

Step 5 — Longest-prefix match

Ask r1 which route it would use for three different destinations:

r1 ip route get 10.NN.32.10
r1 ip route get 10.NN.33.10
r1 ip route get 10.NN.40.1

10.NN.32.10 matches both routes, and r1 picks the /24 (via r2) because it's longer — more specific. The other two only match the /20, so they go via r3.

Step 6 — See the paths

h1 traceroute -n -I 10.NN.32.10
h1 traceroute -n -I 10.NN.33.10

h2 is three hops away, h3 is four — through r3. Look closely at h3's hop 3: it shows 10.NN.12.2, r2's address on the r1–r2 link, even though the packet arrived from r3. Keep that in mind for the write-up.

Step 7 — Remove routes and watch the fallback

Delete r1's specific route, then trace to h2 again:

r1 ip route del 10.NN.32.0/24
h1 traceroute -n -I 10.NN.32.10

h2 still answers, but now through r3: the /20 catches what the /24 used to. Then take away r3's route:

r3 ip route del 10.NN.32.0/20
h1 traceroute -n -I 10.NN.32.10

The trace stops at r3 with !N — network unreachable. r3 is the router that ran out of routes.

Step 8 — Make a routing loop

Point r3's /20 route back at r1:

r3 ip route add 10.NN.32.0/20 via 10.NN.13.1
h1 ping -c 2 10.NN.32.10
h1 traceroute -n -I -m 8 10.NN.32.10

Ping now reports Time to live exceeded, and the trace bounces r1, r3, r1, r3… r1 sends the packet to r3, r3 sends it back, and every router hop decrements the TTLTTLTime To Live: a counter in every IP packet that each router decreases by one. At zero the packet is discarded, which stops packets looping forever. until it reaches zero. The TTL is what stops a loop from going on forever.

Step 9 — The same decisions in IPv6

Everything so far was IPv4; the routers also have IPv6 addresses, but IPv6 forwarding is switched off and has its own routing table. Do it again in IPv6 — forwarding on, then the same overlapping routes:

r1 sysctl -w net.ipv6.conf.all.forwarding=1
r2 sysctl -w net.ipv6.conf.all.forwarding=1
r3 sysctl -w net.ipv6.conf.all.forwarding=1
r1 ip -6 route add fd00:NNNN:32::/64 via fd00:NNNN:12::2
r1 ip -6 route add fd00:NNNN:30::/44 via fd00:NNNN:13::2
r3 ip -6 route add fd00:NNNN:30::/44 via fd00:NNNN:23::2
r3 ip -6 route add fd00:NNNN:1::/64 via fd00:NNNN:13::1
r2 ip -6 route add fd00:NNNN:1::/64 via fd00:NNNN:12::1
h1 ping -6 -c 3 fd00:NNNN:32::10
h1 ping -6 -c 3 fd00:NNNN:33::10

The first reply can take a couple of seconds while each router finds its neighbours with Neighbour Discovery, IPv6's counterpart of ARPARPAddress Resolution Protocol: how a host finds the MAC address for an IP address on its local network — it broadcasts a request, and caches the reply.. The broad route is a /44 because IPv6 addresses are hexadecimal: the first 44 bits fix fd00:NNNN:3, so the route covers fd00:NNNN:30:: to fd00:NNNN:3f:ffff:… — both LANs, like the /20 in IPv4.

Then repeat Steps 5 and 6 in IPv6:

r1 ip -6 route get fd00:NNNN:32::10
r1 ip -6 route get fd00:NNNN:33::10
r1 ip -6 route get fd00:NNNN:3f::1
h1 traceroute -6 -n -I fd00:NNNN:33::10

Longest-prefix match works exactly as in IPv4: the /64 wins for h2, and the rest go via r3. Now look at hop 3 of the trace to h3. Compare it with hop 3 in Step 6.
