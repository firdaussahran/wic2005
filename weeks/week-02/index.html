1 · Automation is data

Last week ended with a question: if box-by-box CLI doesn't scale, what does a program need instead? Look at what a router gives you today when you ask about its interfaces:

Router# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     10.0.0.1        YES manual up                    up
GigabitEthernet0/1     unassigned      YES unset  administratively down down

That's written for a person. A program has to guess where each column starts, and the guess breaks when a vendor adds a column or a name gets longer. Now the same information as data:

{
  "interfaces": [
    { "name": "GigabitEthernet0/0", "ip": "10.0.0.1", "enabled": true },
    { "name": "GigabitEthernet0/1", "ip": null, "enabled": false }
  ]
}

Every value has a name and a type. A program can read it, check it, change it and send it back — without guessing.

The big idea of the course

Automation is the manipulation of structured representations of network state. Configuration, operational state, inventories and topologies all become data that programs read, check, transform and write. Everything later in this course — YANGYANGA data modelling language for network configuration and state. NETCONF, RESTCONF and gNMI all carry data structured by YANG models., NETCONFNETCONFA network management protocol, usually over SSH, that exchanges YANG-modelled data as XML and supports transactions: candidate datastore, commit and locking., AnsibleAnsibleAn agentless automation tool: playbooks describe the desired state, and modules apply it to devices over SSH or APIs., telemetry — is a variation on that.

2 · One model, many serialisations

Two ideas that are easy to blur:

  • A data model is the structure of the information: a device has a hostname and a list of interfaces; each interface has a name, an IP address and an enabled flag.
  • A serialisation is how that structure is written down as text, to store it or send it: JSON, YAML or XML.

3 · When data lies

Structured data removes the guessing — but only if the data means what you think it means.

YAML's surprises

YAML guesses a value's type from how it looks, and Python's popular PyYAML library follows the older YAML 1.1 rules. Here's what it actually returns (checked with PyYAML 6.0.1, the version in the course lab image):

You writeYou meantPython gets
country: NOthe text "NO"False
enabled: yesthe text "yes"True
port: 010ten8 — read as octal
time: 1:30a time90 — read as base 60
version: 1.10version "1.10"1.1 — a float
vlan: 0800VLAN "0800"the text '0800' — inconsistent with 010

The fix is simple: quote anything that isn't obviously a number or a word — country: "NO", version: "1.10". And YAML refuses tabs for indentation; always use spaces.

Quick check

A site inventory in YAML says country: NO for the Oslo office. Loaded with Python's PyYAML, what is the value of country?

Valid is not the same as correct

A parser checks syntax: are the brackets, colons and indentation right? It knows nothing about meaning: two hosts sharing an IP address, an interface on a switch that doesn't exist, a VLAN number above 4094. Data can be perfectly valid YAML and still describe a broken network.

That's why serious automation validates data before using it — with its own checks (your check() function in this week's lab) or with a schema that describes what's allowed (YANG, from Week 8).

Quick check

build_topo.py loads a topology file with no YAML errors at all — but two hosts have the same IP address. How would you describe that file?

Loops: doing it for every device

The point of having data is that one piece of code handles every device:

import yaml

with open("inventory.yaml") as f:
    inventory = yaml.safe_load(f)

for device in inventory["devices"]:
    for iface in device["interfaces"]:
        print(device["name"], iface["name"], iface["ip"])

sw1 eth0 10.0.0.1/24
sw1 eth1 10.0.1.1/24
r1 eth0 10.0.0.254/24

Functions and exceptions: when the data isn't there

Real data has gaps. Asking a dictionary for a key it doesn't have raises a KeyError — Python's way of refusing to guess. Wrap lookups in a function, and decide deliberately what happens when something is missing:

def interface_ips(inventory, device_name):
    """Return the IP addresses of one device's interfaces."""
    for device in inventory["devices"]:
        if device["name"] == device_name:
            return [iface["ip"] for iface in device["interfaces"]]
    raise KeyError(f"no device called {device_name!r}")

try:
    print(interface_ips(inventory, "r2"))
except KeyError as err:
    print("Lookup failed:", err)

Lookup failed: "no device called 'r2'"

A script that stops with a clear message is far safer than one that carries on with a wrong guess — especially one about to change 40 switches.

5 · Version control for configuration

If configuration is data, it deserves what programmers give their code: version control. Git records every change as a commit — a snapshot with an author, a time and a message, pointing back to the commit before it. That gives you, for every change to every device:

  • History — what the configuration was last Tuesday, and every version since.
  • Diffs — exactly which lines changed, and nothing else.
  • Review — a colleague can read the diff before it goes anywhere near a device.
  • Rollback — when something breaks, go back to the last good version.
  • Accountability — who changed what, when, and why.

Step through a small Git workflow — the same one you'll use in this week's lab — and watch the history grow:

Step through: Git, one command at a time

Step 1 of 7

git init

Creates an empty repository: a hidden .git folder that will hold every version. Nothing is tracked yet.

Reading a diff

A diff is the most useful thing Git shows you. Lines starting with + were added, - were removed, and the rest is context so you can see where the change sits:

 hosts:
   - name: h2
-    ip: 10.0.0.2/24
+    ip: 10.0.0.20/24

One host's address changed — and nothing else did. Compare that with diffing two folders of copies named sw1-final.cfg and sw1-final-v2-REAL.cfg.

Branches and conflicts

A branch lets a change be developed and reviewed without touching the main configuration. When two branches change different lines, Git merges them automatically. When they change the same lines, Git stops and asks a person to decide — a merge conflict. That's not Git failing: it's Git refusing to guess, exactly like the KeyError above.

Quick check

What does keeping device configurations in Git give you that a folder of copies (sw1-final-v2-REAL.cfg) doesn't?

Wrap-up

Key takeaways

  • Automation is the manipulation of structured data about the network: read it, check it, transform it, write it.
  • A data model is the structure; JSON, YAML and XML are serialisations of it. The model is what matters.
  • Parsing only checks syntax. Valid data can still be wrong — and YAML can quietly turn NO into False. Validate before you act.
  • In Python, parsed data is nested dictionaries and lists; loops and functions let one piece of code handle every device, and exceptions stop it when data is missing.
  • Configuration belongs in Git: history, diffs, review, rollback and accountability for every change.

Before next week

Open a configuration or inventory file you use — for a router, a game server, anything — and ask: what is its data model, and which serialisation is it written in? Could it be written in another one without losing anything?

Lab

Goal

Describe a network as data, and let a script build it. Change the data, and the network changes. This is the idea the whole course rests on: automation is the manipulation of structured representations of network state.

Like Week 1, this lab is short and light.

Before the lab

  • GitGitA version control system that records every change to a set of files as a commit, so you can see, compare and undo changes. installed on your laptop (git --version), and an account on GitHub (or your institution's Git host).
  • A code editor (VS Code works well).
  • The Week 1 setup: DockerDockerA tool for packaging and running software in containers: isolated processes with their own filesystem and network namespace. and the course container.

Step 1 — Get the files

Make a folder called netlab for your lab work this semester, and download these two files into it:

  • build_topo.py — a short Python script that reads a network description and builds it in MininetMininetA tool that emulates a network of hosts, switches and links on one Linux machine, using network namespaces..
  • topology.yaml — the description: one switch, three hosts.

Open both in your editor and read them. The whole network is about 20 lines of YAMLYAMLA human-friendly text format for structured data that uses indentation. Common for configuration files..

Your addresses

Every lab from Week 2 on uses addresses that are yours alone, taken from your student ID. Wherever the instructions show NN or NNNN, type your own numbers:

NNNN
the last 4 digits of your student ID, e.g. 4207
NN
the last 2 digits, as a number without a leading zero: 07 becomes 7
Your blockFor an ID ending 4207
IPv410.NN.0.0/1610.7.0.0/16

Your outputs then show your own addresses — part of what makes your submission recognisably yours. If you work with a partner, each of you runs the lab with your own numbers. If your last four digits start with a zero, Linux shortens the address when it prints it: fd00:0042::1 appears as fd00:42::1, and they’re the same address.

Only ever put the last 4 digits in your files, never your full student ID: your repository may be public.

Make the file yours. In topology.yaml, replace NNNN with the last 4 digits of your student ID and every NN with the last 2 — for an ID ending 4207, student_id_last4: "4207", h1 is 10.7.0.1/24 and fd00:4207::1/64. build_topo.py checks your addresses before it builds anything, and stops with a PROBLEM message if any are still placeholders or outside your blocks.

Step 2 — Build the network from the file

From your netlab folder, start the course container as in Week 1:

docker run -it --rm --privileged -v "${PWD}:/lab" -w /lab firdaussahran/netlab-mininet:1.0

Inside the container:

python3 build_topo.py topology.yaml

At the mininet> prompt, run net and pingall: the network described in the file now exists. pingall only tests IPv4, so try IPv6 by hand, then look at h1's neighbour table:

h1 ping -6 -c 1 fd00:NNNN::2
h1 ip neigh

h1 now knows h2's MAC addressMAC addressThe hardware address of a network interface, such as 00:00:00:00:00:01. Ethernet switches forward frames by MAC address. twice: once for 10.NN.0.2, learned with ARPARPAddress Resolution Protocol: how a host finds the MAC address for an IP address on its local network — it broadcasts a request, and caches the reply. as in Week 1, and once for fd00:NNNN::2, learned with IPv6's Neighbour Discovery, which uses ICMPv6 messages instead of ARP. Same question — "which MAC has this address?" — answered by a different protocol for each IP version.

Type exit to leave Mininet, but stay in the container — you'll build again in a moment.

Two terminals from now on

Keep two terminals open: the container for running Mininet, and your laptop for Git. Edit files in your editor on the laptop — the container sees the same folder.

Step 3 — Start your Git repository

In the laptop terminal, inside netlab:

git init
git add build_topo.py topology.yaml
git commit -m "Week 2: starting topology"

Step 4 — Grow the network by editing data

In topology.yaml, add a second switch s2, a host h4 with ip: 10.NN.0.4/24 and ipv6: fd00:NNNN::4/64, and two links: [h4, s2] and [s1, s2]. Rebuild it in the container and run pingall: you should get 12/12 replies across both switches.

Then on the laptop, look at exactly what changed and commit it:

git diff
git commit -am "Add s2 and h4"

Step 5 — Same data, different format

In the container, convert the YAML file to JSONJSONJavaScript Object Notation: a minimal text format for structured data — objects, arrays, strings, numbers, booleans and null.:

python3 -c "import yaml, json; print(json.dumps(yaml.safe_load(open('topology.yaml')), indent=2))" > topology.json

Build from the JSON file — python3 build_topo.py topology.json — and run pingall: an identical network. Open both files side by side. The data model (switches, hosts, links) is the same; only the serialisation differs. What did the JSON version lose?

Show answer

The comments. JSON has no comment syntax, so they were dropped in the conversion — and nothing about the network changed, because comments were never part of the data model, only of one serialisation of it.

Step 6 — Bad data, quiet failure

Give h4 the same addresses as h2 — change them to 10.NN.0.2/24 and fd00:NNNN::2/64 — then rebuild and run pingall. It reports only one failure out of 12: the network looks almost healthy. Two hosts now answer to the same IPv4 address, and which one replies depends on which answers ARP first. In a real network, this is the kind of fault that wastes an afternoon.

IPv6 behaves differently. Look at both hosts' IPv6 addresses:

h2 ip -6 addr show dev h2-eth0
h4 ip -6 addr show dev h4-eth0

One of them has marked fd00:NNNN::2 as dadfailed and stopped using it. Before an IPv6 host uses a new address, it asks the network whether anyone else already has it — Duplicate Address Detection — and backs off if they do. IPv4 has no such check built in.

Neither protocol stops the bad network from being built, though. Catch it before that instead: in build_topo.py, fill in the check() function so it reports any address — IPv4 or IPv6 — used by more than one host.

Show hint

Loop over spec["hosts"]. For each host and each of its addresses (ip, and ipv6 if it has one), strip the prefix length — everything from the / — and remember each address you've seen in a dictionary that maps address → host name. If an address is already in the dictionary, append a problem message to problems.

When it works, building the bad file stops with messages like:

PROBLEM: h4 and h2 both use 10.NN.0.2
PROBLEM: h4 and h2 both use fd00:NNNN::2

Put h4 back to 10.NN.0.4/24 and fd00:NNNN::4/64, confirm it builds again, and commit:

git commit -am "Check for duplicate IP addresses"

git remote add origin <your repository URL>
git push -u origin main

Troubleshooting

git commit says "Please tell me who you are"

Cause: Git needs your identity set once per machine before it will let you commit.

Fix:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Then repeat the git commit command.

git push asks for a password and rejects it

Cause: GitHub (and most Git hosts) no longer accept your account password for git push — you need a Personal Access Token or SSH key instead.

Fix: on GitHub, go to Settings → Developer settings → Personal access tokens → generate one, and paste it in place of your password when prompted. Ask your lecturer if your institution uses a different Git host with different steps.

python3 build_topo.py says "No such file or directory"

Cause: the container was started from a different folder, so /lab doesn't contain your files.

Fix: exit the container, cd into your netlab folder on the laptop, and start the container again from there. Inside, ls should show build_topo.py and topology.yaml.

The build stops with PROBLEM: … isn't in your block or isn't a valid address

Cause: an address in topology.yaml still has NN or NNNN in it, or doesn't match student_id_last4.

Fix: check "Your addresses" at the top of the lab. With an ID ending 4207, every IPv4 address starts 10.7. and every IPv6 address starts fd00:4207:. NN never has a leading zero: 10.07.0.1 isn't valid.

The build fails with a yaml error, or KeyError

Cause: a typo in topology.yaml — usually indentation (YAML uses spaces, never tabs), a missing -, or a misspelled key like host instead of hosts.

Fix: compare your file line by line with the original. The error message usually gives the line number.
