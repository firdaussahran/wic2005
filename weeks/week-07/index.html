1 · From screens to APIs

In Week 1, a script that logs in over SSH and parses CLI output broke whenever the output changed. In Week 2, data with names and types fixed that. In Week 4, a controller offered applications a northbound APInorthbound APIThe interface between a controller and the applications that use it — usually a REST API.. This week is about that interface: an API is a contract — documented resources, operations, data formats and errors — that a program can rely on.

Most network APIs run over HTTP: it's everywhere, it gets through firewalls, it's secured by TLS, and every language and tool can speak it. Controllers, cloud networks and many devices expose REST APIs. And in Week 9, RESTCONFRESTCONFAn HTTP-based protocol that exposes YANG-modelled data as REST resources, in JSON or XML. is this same idea applied to the data models you'll meet in Week 8.

2 · HTTP as a foundation

Every HTTP exchange is one request and one response, both plain text with the same shape: a first line, headers, a blank line, and an optional body.

PUT /api/v1/vlans/30 HTTP/1.1
Host: api.lab.example
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/json

{"name": "guest"}

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/vlans/30

{"id": 30, "name": "guest"}
  • The method says what to do; the path says to what. A query string, such as ?limit=50, refines it.
  • Headers carry everything else. Authorization says who you are. Content-Type says what format the body is in, and Accept says what you'd like back. Week 9's RESTCONF, for instance, asks for application/yang-data+json.
  • The status code is the server's verdict, and your code must act on it:
CodeMeaningWhat your client should do
200 OKIt worked; the body has the resultUse it
201 CreatedA new resource exists; Location says whereNote where it is
204 No ContentIt worked; nothing to returnCarry on
400 Bad RequestThe request is malformedFix your code — don't retry
202 AcceptedAccepted, but not done yet: the work happens laterPoll the status it points to, or wait for a callback
401 UnauthorizedWho are you? Missing or expired credentialsAuthenticate again — the WWW-Authenticate header says how
403 ForbiddenI know who you are, and you may notDon't retry; get the permission
404 Not FoundNo such resourceCheck the URL or ID
409 ConflictClashes with the current stateRead the state, then decide
422 Unprocessable ContentWell-formed, but the values are invalidFix the data
429 Too Many RequestsSlow downWait for Retry-After, then retry
500 Internal Server ErrorThe server failedRetry carefully, and report it
503 Service UnavailableTemporarily unavailableRetry with backoff

The rule of thumb: 4xx means the problem is your request, so don't blindly retry (except 429). 5xx means the problem is the server, so an idempotent request can be retried later.

3 · REST: constraints and what they buy


REST is an architectural style, described by Roy Fielding in 2000. It's a set of constraints, each of which buys something:


ConstraintWhat it meansWhat it buys a network controller
Client–serverClients and the server evolve separatelyScripts, GUIs and AnsibleAnsibleAn agentless automation tool: playbooks describe the desired state, and modules apply it to devices over SSH or APIs. all drive one controller
StatelessEvery request carries everything needed, credentials includedAny replica can answer any request; retries and load balancing are easy
CacheableResponses say whether they can be reusedFewer repeated reads of slow-changing state
Uniform interfaceResources have URLs, and standard methods act on representations of themGeneric tools work everywhere: curl, Postman, Ansible's uri module
Layered systemClients can't tell what sits in betweenGateways, rate limiters and TLS terminators can sit in front
Code on demand (optional)The server may send code for the client to runRare in network APIs; the one constraint Fielding made optional


The uniform interface itself has four parts: resources are identified (by URLs); clients change them by sending representations (such as JSONJSONJavaScript Object Notation: a minimal text format for structured data — objects, arrays, strings, numbers, booleans and null.); every message is self-descriptive (its method, headers and media type say how to handle it); and responses carry links to what you can do next — like the next URL of a page, later in this lecture.


That's why good REST URLs name things, not actions. Compare:


    

  • PATCH /api/v1/devices/sw1/interfaces/eth1 with {"enabled": false} — the interface is a resource, and you change its state;
    • 

  • POST /api/v1/disableInterface?device=sw1&if=eth1 — an action dressed up as a URL.
    • 



Many APIs called "REST" bend these rules, and still work. Knowing the constraints tells you what you lose when they do.


Not everything is REST. In an RPC-style API (remote procedure call), the client calls named procedures — GetConfig, SetConfig, Subscribe — instead of acting on resources with standard methods. gRPCgRPCA framework for calling functions on another machine over HTTP/2, with messages encoded as protobuf. gNMI is built on it. is the common example in networking: Week 5's P4RuntimeP4RuntimeAn API, carried over gRPC, that lets a controller load a compiled P4 program into a switch and write entries into its tables at run time. uses it, and so does Week 9's gNMIgNMIgRPC Network Management Interface: gets, sets and streams YANG-modelled data over gRPC, using protobuf encoding.. JSON-RPC and NETCONFNETCONFA network management protocol, usually over SSH, that exchanges YANG-modelled data as XML and supports transactions: candidate datastore, commit and locking. are RPC-style too. RPC can be faster and more precisely typed; REST gives you the uniform interface, so generic tools work. Both can be synchronous (the answer comes back on the same request) or asynchronous (202 Accepted now, the result later).

4 · Idempotency


An operation is idempotent if doing it twice has the same effect as doing it once. That's the central safety property of automation, for one reason: timeouts. When a request times out, you can't know whether the server applied it. If the operation is idempotent, you just send it again. If it isn't, a retry can apply your change twice.


MethodSafe (no change)?Idempotent?Typical use
GETYesYesRead
PUTNoYesCreate or replace a whole resource, at a URL you choose
DELETENoYesRemove
PATCHNoNot by definitionChange some fields — idempotent for "set name", not for "append". It can be made safe, for example by sending it only if the resource hasn't changed
POSTNoNoCreate in a collection, or trigger an action


Your script sends a change; the server applies it; the response is lost. Try each operation, and retry:


Try it: the response is lost — do you retry?
POST /api/v1/acl/entries
{"action": "permit", "src": "10.0.0.0/8"}
    Server state
    ACL entries
    1. permit 192.168.0.0/16
    VLANs
    10 users · 20 voice
    

    Three ways to stay safe:
    

      

    • Declare the desired state with PUT ("VLAN 30 is called guest") instead of describing steps ("add a VLAN"). Week 10's Ansible is built on this idea.
      • 

    • Use an idempotency key with POST: a unique ID, sent in an Idempotency-Key header, that the server remembers, so a retry returns the first result instead of acting again. It's an IETF Internet-Draft, already used by payment APIs such as Stripe.
      • 

    • Check, then act: read the current state before changing it — accepting that it may change in between.
      • 

    

    Quick check
    You send DELETE /api/v1/vlans/20 twice. The first reply is 204 No Content; the second is 404 Not Found. Is DELETE idempotent?

    5 · Who are you, and what may you do?
    

    Two separate questions:
    

      

    • authentication — who is making this request? Failing it gives 401 Unauthorized;
      • 

    • authorisation — is this caller allowed to do this? Failing it gives 403 Forbidden.
      • 

    

    MethodHow it worksGoodWatch out
    Basic authusername:password, base64-encoded, in every requestSimpleBase64 is not encryption: the password travels every time
    API keyA long secret string in a headerEasy for scriptsRarely expires, often over-privileged, hard to rotate
    Bearer tokenLog in once; send Authorization: Bearer <token> until it expiresThe password isn't sent every time; tokens expireYour client must handle expiry and refresh
    OAuth 2.0An authorisation server issues tokens with scopes; machines use the client credentials flowLeast privilegeleast privilegeGiving every account, token and system only the access its job needs — no more — so that a compromise does as little damage as possible., central revocationMore moving parts
    

    Whatever the method: only ever over HTTPS, and never with the secret written into your script — or committed to GitGitA version control system that records every change to a set of files as a commit, so you can see, compare and undo changes. (Week 2). Read it from the environment:

    6 · Real-world APIs: pages, limits and retries
    

    Real APIs protect themselves, and your client has to cooperate:
    

      

    • Pagination — a collection comes back a page at a time: by offset (?offset=100&limit=50), by page number, or by cursor, where each page tells you where the next one starts. Cursors stay correct even when items are added while you read.
      • 

    • Rate limiting — too many requests, and you get 429 Too Many Requests with a Retry-After header saying how long to wait.
      • 

    • Retries with backoff — for timeouts and 5xx errors, wait longer after each failure (1, 2, 4, 8 seconds…), plus a little randomness so that many clients don't retry in step. Only retry idempotent operations.
      • 

    • Versioning — /api/v1/ in the path, or a header, so that the server can change without breaking your script overnight.
      • 

    

    Read all 230 devices from a paginated, rate-limited API. Start with the naive client, then fix it one choice at a time:
    

    Try it: read every device from a real-world API
    The API has 230 devices, returns at most 50 per page, and allows 3 requests a second. Choose how your client behaves:
    Pages
    On 429 Too Many Requests
    TimeGETResponse
    0.0 s/api/v1/devices?limit=50200 50 devices · next: …cursor=d50
    50 / 230 devices · 1 request · 0 × 429
    Finished "successfully" — with 50 of 230 devices. No error, just missing data: the worst kind of bug.
    Simulated: requests are 0.1 s apart, and the limit counts every request — rejected ones too, as many real APIs do.
    

    The fixed client, in Python:
    

    import time
import requests

def get_all(url, token):
    """Follow 'next' links until there are none, waiting whenever we're rate-limited."""
    items = []
    headers = {"Authorization": f"Bearer {token}"}
    while url:
        r = requests.get(url, headers=headers, timeout=5)
        if r.status_code == 429:
            time.sleep(int(r.headers.get("Retry-After", "1")))
            continue                      # same URL again
        r.raise_for_status()              # any other error: stop, loudly
        body = r.json()
        items.extend(body["items"])
        url = body["next"]                # None on the last page
    return items

    

    (Retry-After can also be a date; this handles the common case, a number of seconds.)

    Reading documentation is a skill, and it's faster than guessing. For any new API, find:

      4.

    Wrap-up
    

    Key takeaways
      

    • An API is a contract. HTTP carries it: a method and a path, headers, a body — and a status code your client must act on.
      • 

    • 4xx means fix the request (except 429: wait); 5xx means the server failed, so retry idempotent requests with backoff.
      • 

    • REST's constraints each buy something. Statelessness is what lets any controller replica serve any request.
      • 

    • Idempotency makes retries safe. GET, PUT and DELETE are idempotent; POST isn't — use PUT with the desired state, or an idempotency key.
      • 

    • Authentication (401) and authorisation (403) are different questions. Use HTTPS, short-lived tokens, and keep secrets out of code and Git.
      • 

    • Real clients follow pagination to the end, honour Retry-After, and back off — or they silently miss data, or get locked out.
      •

Run it with the chaos still on and save the audit in lab7/audit-step4.txt: one change per run, however many retries. Then switch the chaos off (-d '{}').
    

    Step 5 — A client that reads everything
    

    Open inventory.py. It logs in with a username and password from the environment, then reads /api/v1/devices a page at a time. Two parts are yours to write: get_page(), which sends one request and deals with whatever comes back, and get_all(), which follows the next links to the end. The docstrings say exactly what each must handle.
    

    Make the API misbehave first, so that your client meets 503s as well as 429s:
    

    curl -s -X PUT http://api:8000/api/v1/lab/chaos -H 'Content-Type: application/json' -d '{"errors_503": 0.2}'
export LAB_USERNAME=netops LAB_PASSWORD=netops-pass
python3 inventory.py | tee lab7/inventory.txt

    

    It must read every device — 200 plus your NN — and the count must match the API's X-Total-Count. Look at devices.json: those are your addresses.
    

    Step 6 — Tokens expire
    

    Restart the API with tokens that last only 5 seconds, and a stricter rate limit of 2 requests a second. In the laptop terminal:
    

    docker rm -f api
docker run -d --name api --network apilab -v "${PWD}:/lab" -w /lab python:3.12 python3 labapi.py --id NNNN --token-ttl 5 --rate 2

    

    Run inventory.py again from the client container (… | tee lab7/expiry.txt). Reading every page now takes longer than 5 seconds, so part-way through, a request comes back 401. Your get_page() should log in again and carry on. Did it?
    

    Step 7 — Read the documentation
    

    The API documents itself:
    

    curl -s http://api:8000/openapi.json | python3 -m json.tool | less

    

    Find, from the document alone: the largest limit the devices endpoint accepts; which methods /api/v1/acl/entries/{id} allows; what the Idempotency-Key header does when it's reused with a different body; and a way to ask for only one site's devices — something the lecture never mentioned. Use it to list the devices at one site with curl.
    

    When you're done, type exit, and stop the API with docker rm -f api.

    Troubleshooting
    

      

    • docker: Error response from daemon: Conflict. The container name "/api" is already in use: an old one is still there. Remove it with docker rm -f api.
      • 

    • network apilab already exists: fine — it's left from last time. Carry on.
      • 

    • curl: (6) Could not resolve host: api: the client isn't on the apilab network. Exit and start it again with --network apilab.
      • 

    • curl: (52) Empty reply from server: that's the chaos you switched on, losing a response. Switch it off with curl -s -X PUT http://api:8000/api/v1/lab/chaos -H 'Content-Type: application/json' -d '{}'.
      • 

    • pip install hangs or fails: some networks block Python's package server. Try another network (a phone hotspot is enough), or install Debian's packages instead — apt-get update && apt-get install -y python3-requests python3-yaml — and run your scripts with /usr/bin/python3 in place of python3.
      • 

    • KeyError: 'LAB_API_TOKEN' (or LAB_USERNAME): the export was in another terminal. Each container shell has its own environment.
      •
